# OOMKilled 원인과 해결 방법

## 무슨 일이 일어나는가

컨테이너가 **memory limit**을 초과하면 리눅스 커널의 cgroup OOM killer가 프로세스를 SIGKILL(종료 코드 137)로 죽입니다. 그러면 kubelet이 `restartPolicy`에 따라 컨테이너를 재시작하고, 같은 메모리 패턴이 반복되면 `CrashLoopBackOff`로 이어집니다.

원인은 크게 네 가지입니다.

1. **limit이 너무 낮음**: 정상 동작에 필요한 메모리가 limit보다 큰 경우입니다.
2. **메모리 누수**: 시간이 지날수록 사용량이 늘어나 결국 limit에 닿는 경우입니다.
3. **순간 피크**: 시작 시점, 대용량 요청, 배치 처리 때 메모리가 급증하는 경우입니다.
4. **런타임이 limit을 모름**: JVM, Node, Go 등이 컨테이너 limit이 아니라 노드 전체 메모리를 기준으로 힙을 잡는 경우입니다.

참고로 노드 전체가 메모리 부족이면 kubelet이 파드를 evict합니다. 이 경우는 `Evicted` 상태로 표시되고 OOMKilled와는 다릅니다.

## 먼저 확인할 것

```bash
# 종료 사유 확인 (Reason: OOMKilled, Exit Code: 137)
kubectl describe pod <pod> | grep -A8 "Last State"

# 현재 사용량 vs limit
kubectl top pod <pod> --containers
kubectl get pod <pod> -o jsonpath='{.spec.containers[*].resources}'

# 직전 컨테이너 로그
kubectl logs <pod> --previous
```

Prometheus를 쓴다면 `container_memory_working_set_bytes`를 limit과 함께 그래프로 보세요.

- **톱니 모양으로 계속 우상향**하면 누수입니다.
- **시작 직후나 특정 시점에 급증**하면 피크입니다.
- **처음부터 limit 근처에서 평평**하면 limit이 부족한 것입니다.

## 무엇을 바꿀 것인가

**1. limit과 request 조정 (가장 흔한 해결책)**

```yaml
resources:
  requests:
    memory: "512Mi"
  limits:
    memory: "1Gi"   # 관측된 피크 + 20~30% 여유
```

- 메모리는 압축할 수 없는 자원이라 request와 limit을 같거나 비슷하게 두는 편이 안정적입니다.
- 단순히 limit만 올리면 누수가 원인일 때 재시작 간격만 늘어납니다. 원인을 함께 확인하세요.

**2. 런타임 설정을 limit에 맞추기**

- JVM: `-XX:MaxRAMPercentage=70` (힙 외에 메타스페이스와 스레드 스택 몫도 남겨야 합니다)
- Node.js: `--max-old-space-size`를 limit보다 작게 설정합니다.
- Go: `GOMEMLIMIT`을 limit의 약 90%로 설정합니다.

**3. 애플리케이션 수정**

- 누수가 의심되면 힙 프로파일링을 합니다 (pprof, heap dump, `memray` 등).
- 대용량 데이터는 통째로 로드하지 말고 스트리밍이나 페이지네이션으로 처리합니다.
- 캐시와 큐에 크기 상한을 둡니다.

**4. 확장 방식 검토**

- 파드당 부하가 크다면 HPA로 replica를 늘려 파드당 메모리 사용량을 줄입니다.
- 사용량 패턴이 불확실하면 VPA를 추천 모드로 돌려 적정값을 확인합니다.

## 정리

1. `describe`로 OOMKilled인지 확인합니다.
2. 메모리 그래프로 누수, 피크, limit 부족 중 어느 쪽인지 판별합니다.
3. limit 부족이면 limit을 올리고, 누수면 코드를 고칩니다. 런타임 설정도 같이 맞춥니다.

사용 중인 언어와 런타임, 현재 resources 설정, `describe` 출력을 알려주시면 구체적인 수치까지 같이 잡아 드리겠습니다.

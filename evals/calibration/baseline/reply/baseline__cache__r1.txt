## 왜 그런가

보통 **cache-aside(lazy loading)** 패턴에 **TTL 10분**을 걸어 둔 구조라서 그렇습니다.

1. 읽기 요청이 오면 Redis를 먼저 조회하고, 있으면 그 값을 반환합니다.
2. 없으면 DB에서 읽어 Redis에 `SET key value EX 600`으로 저장합니다.
3. 가격을 바꾸면 DB만 갱신됩니다. Redis에 남은 키는 TTL이 끝날 때까지 그대로이고, 그 시간이 최대 10분입니다.

즉 쓰기 경로가 캐시를 건드리지 않아서, 만료만이 유일한 갱신 수단입니다.

## 고치는 방법

**1. 쓰기 시 무효화(가장 흔하고 권장)**
- 가격을 갱신하는 코드에서 DB 커밋 **후에** `DEL price:{productId}`를 호출합니다.
- 다음 읽기에서 DB의 새 값으로 캐시가 다시 채워집니다.
- 트랜잭션 안에서 지우면 커밋 전에 다른 요청이 옛 값을 다시 캐싱할 수 있습니다. 반드시 커밋 후에 지우세요.

**2. 쓰기 시 갱신(write-through)**
- DB 커밋 후 새 값을 Redis에 `SET`합니다.
- 읽기 미스가 줄어듭니다. 대신 동시 쓰기가 일어나면 순서가 뒤바뀌어 옛 값이 남을 수 있으니, 버전 번호나 `updated_at` 비교가 필요합니다.

**3. 이벤트 기반 무효화**
- 가격 변경이 여러 서비스나 경로(어드민, 배치, 프로모션)에서 일어난다면, 변경 이벤트(Kafka, outbox, CDC 등)를 구독해 무효화합니다.
- DB를 직접 수정하는 경로가 있어도 누락되지 않습니다.

**4. 보조 안전장치**
- 가격처럼 민감한 데이터는 TTL을 10분에서 30~60초로 줄이거나, 무효화가 실패해도 오래 남지 않도록 짧은 TTL을 함께 둡니다.
- 프로모션처럼 시작 시각이 정해진 가격은 캐시 값에 유효 기간을 넣거나, 키에 버전을 넣습니다(`price:{id}:v{n}`).

## 주의할 점
- **경쟁 상태**: 읽기 요청이 DB에서 옛 값을 읽은 뒤, 쓰기와 `DEL`이 끝난 후에 그 옛 값을 캐시에 넣을 수 있습니다. 이때는 지연 이중 삭제(몇백 ms 후 한 번 더 `DEL`)나 버전 비교로 줄입니다.
- **결제 시점**: 결제나 주문 단계에서는 캐시 값을 쓰지 말고 DB의 가격을 기준으로 검증하세요. 표시 가격만 캐시가 맡는 편이 안전합니다.
- **다른 캐시 계층**: CDN, 브라우저 캐시, 애플리케이션 로컬 캐시(Caffeine 등)가 있으면 Redis만 지워도 옛 가격이 남습니다.

현재 코드의 캐시 읽기/쓰기 위치를 알려 주시거나 이 디렉터리에 코드가 있으면 알려 주세요. 그러면 구체적인 수정 지점까지 짚어 드리겠습니다.

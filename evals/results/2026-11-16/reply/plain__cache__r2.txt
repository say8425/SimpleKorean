원인은 가격을 바꿀 때 Redis 캐시를 지우지 않기 때문일 가능성이 가장 큽니다. 캐시 항목의 TTL(Time To Live, 캐시가 유지되는 시간)이 10분이면, DB를 바꿔도 항목이 만료될 때까지 예전 값을 돌려줍니다. 저는 아직 코드를 보지 않았습니다. 아래는 일반적인 캐시 어사이드(cache-aside, 읽을 때 캐시를 채우는 방식) 구조를 가정한 설명입니다.

## 목록과 상세가 모두 오래되는 이유

- 상세 페이지는 보통 상품 한 건당 키 하나를 씁니다. 예를 들어 `product:123`입니다.
- 목록 페이지는 카테고리, 정렬, 페이지 번호별로 결과 전체를 키 하나에 담습니다. 이 값 안에 가격이 복사되어 있습니다.
- 가격 변경 코드가 이 키들을 모르면 어느 키도 지워지지 않습니다.

## 고치는 방법

1. DB 커밋이 끝난 뒤에 상세 키를 삭제하세요. 삭제하면 다음 읽기에서 새 값으로 캐시가 채워집니다.
2. 목록 캐시에서 가격을 빼세요. 목록에는 상품 ID 순서만 캐시하고, 가격은 상품 단위 키에서 조합합니다. 이러면 키 한 개만 지워도 목록과 상세가 함께 갱신됩니다.
3. 목록 키를 지우기 어려우면 키에 버전 번호를 넣으세요. 예를 들어 `list:v{n}:category:5`입니다. 가격이 바뀔 때 `n`을 올리면 이전 키는 쓰이지 않고 TTL로 사라집니다.
4. TTL을 줄이세요. 이 방법은 오래된 값을 보는 시간만 줄이고 원인을 없애지는 못합니다. 보조 수단으로만 쓰세요.

## 주의할 점

- 삭제는 DB 커밋 뒤에 해야 합니다. 커밋 전에 지우면 다른 요청이 옛 값을 다시 캐시에 채울 수 있습니다.
- 삭제와 재채움 사이에 경쟁(race)이 생길 수 있습니다. 불안하면 몇백 밀리초 뒤에 한 번 더 삭제하세요(지연 이중 삭제).
- 가격 변경이 여러 서비스나 배치 작업에서 일어나면 삭제 코드를 한곳에 모으세요. 이벤트나 CDC(Change Data Capture, DB 변경 감지)로 삭제하면 누락을 막을 수 있습니다.
- 앱 앞에 CDN이나 HTTP 캐시가 있으면 Redis를 지워도 같은 증상이 남을 수 있습니다. `Cache-Control` 헤더도 확인하세요.

가격 변경 코드와 캐시 읽기 코드의 위치를 알려 주시면, 실제 키 구조를 보고 수정 위치를 짚어 드리겠습니다.

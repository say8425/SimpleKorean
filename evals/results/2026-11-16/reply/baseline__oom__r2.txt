클러스터나 매니페스트를 직접 본 건 아니라서, 일반적인 원인과 확인 순서로 설명드립니다.

## 무슨 일이 일어나는 건가

OOMKilled는 컨테이너가 **메모리 limit을 넘어서** 커널의 OOM killer가 프로세스를 강제 종료(exit code 137, SIGKILL)했다는 뜻입니다. 이후 kubelet이 `restartPolicy`에 따라 재시작하고, 같은 일이 반복되면 `CrashLoopBackOff`로 보입니다.

CPU는 limit을 넘으면 throttle만 되지만, 메모리는 회수할 수 없어서 바로 kill됩니다.

API와 워커 파드가 둘 다 죽는다면 원인은 보통 다음 중 하나입니다.

1. **limit이 너무 낮음.** 앱의 정상 사용량이 limit보다 큽니다. 가장 흔한 경우입니다.
2. **런타임 힙이 limit을 모름.** 예를 들어 JVM 힙(`-Xmx`)이나 Node의 `--max-old-space-size`가 컨테이너 limit보다 크거나, 힙 외 메모리(메타스페이스, 스레드 스택, 네이티브 버퍼)를 계산에 넣지 않은 경우입니다.
3. **메모리 누수.** 시간이 지날수록 사용량이 올라가다가 죽는 패턴입니다.
4. **워커의 큰 작업 단위.** 큰 배치, 큰 payload, 큰 파일을 통째로 메모리에 올리거나 동시성(concurrency)이 높은 경우입니다.
5. **API의 트래픽 급증.** 요청 수나 연결 수에 비례해 메모리가 늘어납니다.
6. **공통 원인.** 둘이 같은 이미지, 라이브러리, 설정, 캐시를 쓰거나, 배포 직후부터 시작됐다면 최근 변경이 원인일 수 있습니다.

## 먼저 확인할 것

```bash
# 종료 사유 확인 (Reason: OOMKilled, Exit Code: 137, Last State)
kubectl describe pod <pod> -n <ns>

# 현재 사용량 vs limit
kubectl top pod -n <ns> --containers
kubectl get pod <pod> -n <ns> -o jsonpath='{.spec.containers[*].resources}'

# 직전 컨테이너 로그
kubectl logs <pod> -n <ns> --previous

# 노드 쪽 압박(노드 OOM인지 컨테이너 limit OOM인지 구분)
kubectl describe node <node> | grep -A5 -i "pressure\|allocated"
```

Prometheus를 쓴다면 `container_memory_working_set_bytes`를 limit과 함께 그려 보세요. 사용량이 **계단식으로 오르다 limit에서 죽으면** 누수나 누적 문제이고, **시작 직후나 특정 작업 때 급등하면** 작업 단위나 동시성 문제입니다.

## 바꿀 것

**1. requests/limits를 실측 기반으로 조정합니다.**
```yaml
resources:
  requests:
    memory: "512Mi"   # 평소 사용량(p50~p90) 기준
  limits:
    memory: "1Gi"     # 피크 사용량 + 20~30% 여유
```
- requests와 limits를 같게 두면 QoS가 Guaranteed가 되어 노드 압박 시 evict 우선순위가 낮아집니다.
- 단순히 limit만 올리면 누수는 시간만 늦춰질 뿐입니다. 그래서 위 그래프로 원인부터 구분해야 합니다.

**2. 런타임 설정을 limit에 맞춥니다.**
- JVM: `-XX:MaxRAMPercentage=70` 정도로 두고, `-Xmx`를 limit과 같게 두지 않습니다.
- Node: `--max-old-space-size`를 limit의 약 75% 이하로 둡니다.
- Python/Go: Go는 `GOMEMLIMIT`을 limit의 약 90%로 두고, Python은 워커 수와 프로세스당 메모리를 곱해서 계산합니다.

**3. 워커는 작업 방식을 바꿉니다.**
- 동시성(concurrency, prefetch)을 줄입니다.
- 큰 데이터는 스트리밍이나 청크 단위로 처리합니다.
- 작업당 메모리를 제한합니다. 예를 들어 N개 처리 후 프로세스를 재시작하는 `max-tasks-per-child` 같은 설정이 있습니다.

**4. API는 스케일링과 보호 장치를 둡니다.**
- HPA(메모리 또는 요청 수 기준)를 추가하고, 요청 크기와 응답 크기 제한, 커넥션 풀 상한을 설정합니다.

**5. 누수가 의심되면** 힙 프로파일링(heap dump, pprof, `memray` 등)을 해서 근본 원인을 고쳐야 합니다.

## 알려주시면 더 구체적으로 도와드릴 수 있는 것

- 사용 언어와 런타임(JVM, Node, Python, Go 등)
- 현재 `resources` 설정과 `kubectl top` 결과
- 재시작 주기(몇 분 또는 몇 시간 만에 죽는지)와 최근 배포나 설정 변경 여부
- `kubectl describe pod`의 `Last State` 부분

매니페스트나 Helm values 파일이 있으면 경로를 알려 주세요. 파일을 보고 구체적인 수치를 제안해 드리겠습니다.

샤딩은 거의 마지막 수단입니다. 4천만 행은 Postgres 한 대가 충분히 감당하는 크기이고, 보통 인덱스·쿼리 문제로 느린 경우가 대부분입니다. 아래 순서로 보세요.

**1. 느린 쿼리부터 특정하기**
- `pg_stat_statements`를 켜고 총 소요 시간 기준 상위 쿼리를 뽑습니다. 목록·검색 화면이 실제로 날리는 쿼리가 무엇인지 확인합니다.
- 해당 쿼리에 `EXPLAIN (ANALYZE, BUFFERS)`를 실행합니다. Seq Scan, 큰 Sort, 많은 디스크 읽기(`shared read`)가 보이는지 확인합니다.
- `auto_explain`으로 느린 쿼리(예: 500ms 초과)를 로깅해 두면 재현이 어려운 경우에도 도움이 됩니다.

**2. 목록 화면의 전형적인 원인**
- **OFFSET 페이지네이션**: `OFFSET 100000`은 앞의 행을 전부 읽고 버립니다. keyset(커서) 페이지네이션으로 바꾸세요: `WHERE (created_at, id) < (:last_created_at, :last_id) ORDER BY created_at DESC, id DESC LIMIT 50`.
- **정렬용 인덱스 부재**: `WHERE` 조건 + `ORDER BY`에 맞는 복합 인덱스가 필요합니다. 예: `(user_id, created_at DESC)`.
- **`COUNT(*)`로 전체 건수 표시**: 4천만 행에서는 비쌉니다. 근사치(`pg_class.reltuples`)를 쓰거나, "다음 페이지 있음"만 표시하거나, 캐시하세요.
- **`SELECT *`**: 큰 컬럼(JSON, text)이 있으면 필요한 컬럼만 고르고, 가능하면 covering index(`INCLUDE`)로 index-only scan을 노리세요.

**3. 검색 화면의 전형적인 원인**
- `LIKE '%키워드%'`나 `ILIKE`는 일반 B-tree 인덱스를 못 탑니다. `pg_trgm` + GIN 인덱스를 쓰거나, 전문 검색이면 `tsvector` + GIN을 쓰세요. 한국어는 형태소 분석이 필요하면 `pg_bigm`이나 별도 검색 엔진(Elasticsearch/OpenSearch)을 고려하세요.
- `lower(col)` 같은 함수를 쓰면 표현식 인덱스가 필요합니다.
- 조건 일부만 쓰는 필터는 부분 인덱스(`WHERE deleted_at IS NULL` 등)로 크기를 줄일 수 있습니다.

**4. 테이블·DB 상태 점검**
- `pg_stat_user_tables`에서 dead tuple 비율과 마지막 autovacuum 시점을 확인합니다. bloat가 심하면 `pg_repack`을 고려하세요.
- `ANALYZE` 통계가 오래됐거나 부정확하면 플래너가 잘못된 계획을 고릅니다. 필요하면 `default_statistics_target`을 올리세요.
- 메모리 설정을 확인합니다: `shared_buffers`(RAM의 약 25%), `effective_cache_size`, `work_mem`(정렬·해시 spill 여부), `random_page_cost`(SSD면 1.1 정도).
- 안 쓰는 인덱스나 중복 인덱스는 쓰기를 느리게 하니 정리합니다.

**5. 그래도 부족하면 (샤딩 이전 단계)**
- **읽기 복제본**: 목록·검색 같은 읽기 트래픽을 replica로 분산합니다. 읽기가 병목이면 샤딩보다 훨씬 간단합니다.
- **캐시**: 자주 보는 목록 첫 페이지나 인기 검색 결과를 Redis 등에 캐시합니다.
- **파티셔닝**: 시간이나 테넌트 기준으로 대부분의 쿼리가 특정 범위만 건드린다면 선언적 파티셔닝이 효과적입니다. 오래된 데이터를 분리·보관하기도 쉽습니다.
- **검색 분리**: 복잡한 검색은 전용 검색 엔진으로 옮기는 편이 낫습니다.

**샤딩이 의미 있는 경우**는 쓰기 처리량이 단일 노드 한계에 닿았거나, 데이터가 수 TB 이상이라 단일 노드에 못 담는 경우입니다. 읽기가 느린 문제만으로는 거의 해당되지 않습니다. 샤딩하면 조인, 트랜잭션, 리밸런싱, 운영 복잡도가 크게 올라갑니다.

**제안**: 먼저 느린 쿼리 2~3개의 `EXPLAIN (ANALYZE, BUFFERS)` 결과와 테이블 스키마, 기존 인덱스 목록(`\d+ 테이블명`)을 공유해 주세요. 구체적으로 어떤 인덱스나 쿼리 수정이 필요한지 같이 볼 수 있습니다.

## 원인

curl이 서버 인증서의 발급자(CA)를 신뢰 목록에서 찾지 못해서 생기는 오류입니다. 개발·스테이징 서버가 둘 다 같은 증상이면 서버마다 문제가 있다기보다 **사내 CA(사설 루트/중간 인증서)를 내 환경이 모른다**는 쪽일 가능성이 가장 높습니다. 흔한 원인은 세 가지입니다.

1. **사내 사설 CA로 서명한 인증서**를 쓰는데, curl이 쓰는 CA 번들에 그 루트 CA가 없는 경우
2. **서버가 중간 인증서를 같이 보내지 않는 경우**(체인 불완전). 브라우저는 중간 인증서를 자동으로 받아오지만 curl은 받아오지 않아서, 브라우저에서는 되는데 curl에서만 실패합니다.
3. **프록시나 보안 장비가 TLS를 가로채는 경우**(SSL inspection). 이때는 장비의 인증서가 내려오므로 그 CA를 신뢰해야 합니다.

## 원인 확인

```bash
# 서버가 보내는 인증서 체인과 verify 결과 확인
openssl s_client -connect api-dev.example.com:443 -servername api-dev.example.com -showcerts </dev/null
```

- 출력의 `Verify return code: 21 (unable to verify the first certificate)`는 서버가 중간 인증서를 빠뜨렸다는 뜻입니다. 이 경우는 서버 쪽 수정이 필요합니다.
- `Verify return code: 20 (unable to get local issuer certificate)`나 `19 (self-signed certificate in certificate chain)`는 내 쪽에 루트 CA가 없다는 뜻입니다.
- `issuer=` 줄에서 누가 발급했는지 볼 수 있습니다. 사내 CA 이름이면 1번이나 3번입니다.

## 해결

**사내 루트 CA를 받아서 신뢰시키는 방법(권장)**

사내 보안팀이나 IT 위키에서 루트 CA `.crt`(PEM)를 받은 뒤 다음 중 하나를 사용하세요.

```bash
# 1) 한 번만 지정
curl --cacert /path/to/company-root-ca.pem https://api-dev.example.com/...

# 2) 환경변수로 지정(셸 설정에 추가)
export CURL_CA_BUNDLE=/path/to/company-root-ca.pem
```

macOS라면 시스템 키체인에 등록할 수도 있습니다. 다만 Homebrew curl은 키체인 대신 자체 번들을 쓸 수 있어서, 이 경우 `--cacert`가 더 확실합니다.

```bash
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain company-root-ca.pem
```

**서버가 중간 인증서를 빠뜨린 경우**

서버나 로드밸런서에 `fullchain`(서버 인증서와 중간 인증서를 합친 파일)을 설정하도록 인프라 담당자에게 요청하세요. 개발·스테이징이 같은 방식으로 배포되었다면 둘 다 같은 실수를 했을 수 있습니다.

## 피해야 할 것

`curl -k`(`--insecure`)는 검증을 끄므로 임시 확인용으로만 쓰세요. 스크립트나 CI에 넣어 두면 중간자 공격에 노출됩니다.

`openssl s_client`의 `issuer=`와 `Verify return code` 출력을 알려 주시면 어느 경우인지 바로 짚어 드리겠습니다.

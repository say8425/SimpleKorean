샤딩(데이터를 여러 DB 서버에 나누어 저장하는 방식)은 마지막 수단입니다. 4천만 행은 Postgres 한 대가 충분히 감당하는 크기이고, 대부분 인덱스나 쿼리 문제입니다.

## 먼저 할 일

1. 느린 쿼리를 찾아야 합니다. `pg_stat_statements` 확장을 켜면 총 소요 시간이 큰 쿼리 순으로 볼 수 있습니다. 목록 화면과 검색 화면이 보내는 쿼리를 이 목록에서 찾으세요.
2. 그 쿼리의 실행 계획(쿼리를 처리하는 순서와 방식)을 확인해야 합니다.

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
```

3. 실행 계획에 `Seq Scan`(테이블 전체 읽기)이 보이면 인덱스가 없거나 쓰이지 않는 것입니다. 예상 행 수와 실제 행 수가 크게 다르면 통계가 오래된 것이므로 `ANALYZE 테이블명;`을 실행하세요.

## 화면별 원인

목록 화면은 보통 아래 둘 중 하나입니다.

- `OFFSET`이 큽니다. 페이지가 깊어질수록 앞의 행을 모두 읽고 버립니다. 키셋 페이지네이션(마지막으로 본 행의 값 뒤부터 읽는 방식)으로 바꾸세요.
- `ORDER BY`와 `WHERE`에 맞는 복합 인덱스가 없습니다. 필터 칼럼과 정렬 칼럼을 함께 묶은 인덱스를 만드세요.

또 전체 건수를 보여 주려고 `COUNT(*)`를 매번 실행하면 느립니다. 근사값을 쓰거나 "다음 페이지 있음"만 알려 주는 방식으로 바꾸세요.

검색 화면은 `LIKE '%키워드%'`가 원인인 경우가 많습니다. 일반 인덱스는 앞부분이 고정되지 않은 패턴에 쓰이지 않습니다. 다음 중 하나로 바꾸세요.

- 부분 문자열 검색은 `pg_trgm` 확장과 GIN 인덱스를 씁니다.
- 단어 검색은 `tsvector` 전문 검색을 씁니다.
- 한국어 형태소 분석이 필요하거나 검색 요구가 복잡하면 Elasticsearch나 OpenSearch를 검토하세요.

## 그다음 단계

- 테이블 팽창(bloat, 삭제된 행이 차지하는 낭비 공간)과 autovacuum 설정을 확인하세요. 갱신이 잦은 테이블이면 효과가 큽니다.
- 자주 쓰는 조건이 일부 행에 몰려 있으면 부분 인덱스를 쓰세요. 조회 칼럼이 몇 개뿐이면 커버링 인덱스(`INCLUDE`)로 테이블 접근을 줄일 수 있습니다.
- `shared_buffers`, `work_mem`, `effective_cache_size`가 기본값이면 서버 메모리에 맞게 조정하세요.
- 읽기가 많으면 읽기 복제본(read replica)으로 조회를 나누거나 Redis 같은 캐시를 앞에 두세요.
- 오래된 데이터를 거의 조회하지 않으면 날짜 기준 파티셔닝(한 테이블을 여러 조각으로 나누는 기능)을 검토하세요. 샤딩과 달리 서버는 하나입니다.

## 샤딩을 검토할 시점

위 단계를 모두 끝냈는데도 쓰기 처리량이나 저장 용량이 서버 한 대의 한계를 넘으면 그때 샤딩을 검토하세요. 샤딩은 조인, 트랜잭션, 운영 복잡도를 크게 높입니다. 지금은 읽기 지연이 문제이므로 해당하지 않을 가능성이 높습니다.

`EXPLAIN (ANALYZE, BUFFERS)` 결과와 느린 쿼리 하나를 주시면 구체적인 인덱스 설계를 도울 수 있습니다.

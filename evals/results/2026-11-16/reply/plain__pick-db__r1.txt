4천만 행은 샤딩(데이터를 여러 서버에 나눠 저장함)이 필요한 규모가 아닙니다. 먼저 느린 쿼리가 왜 느린지 확인해야 합니다. 대부분 인덱스, 페이지네이션, 통계 문제입니다.

## 1단계: 원인 확인

1. 확장 기능 `pg_stat_statements`를 켜고 총 실행 시간이 큰 쿼리를 찾으세요.
2. 그 쿼리에 아래 명령을 실행하세요.

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
```

3. 실행 계획에서 `Seq Scan`, 큰 `Rows Removed by Filter`, 디스크 정렬(`Sort Method: external merge`)을 찾으세요.

운영 DB에서 `ANALYZE`가 붙은 `EXPLAIN`은 쿼리를 실제로 실행합니다. `INSERT`나 `UPDATE`에는 트랜잭션과 `ROLLBACK`으로 감싸야 합니다.

## 2단계: 화면별 해결

목록 화면:
- `OFFSET`이 크면 느려집니다. 마지막으로 본 값을 기준으로 다음 페이지를 읽는 keyset 페이지네이션(`WHERE (created_at, id) < (...) ORDER BY created_at DESC, id DESC LIMIT 20`)으로 바꾸세요.
- `WHERE` 조건과 `ORDER BY`에 맞는 복합 인덱스를 만드세요. 열 순서가 중요합니다.
- 전체 건수가 필요 없으면 `COUNT(*)`를 빼세요. 필요하면 근사치나 캐시를 쓰세요.

검색 화면:
- `LIKE '%키워드%'`는 일반 인덱스를 못 씁니다. `pg_trgm` 확장과 GIN 인덱스를 쓰세요.
- 형태소 검색이 필요하면 `tsvector`와 GIN 인덱스를 쓰세요. 한국어는 별도 사전이 필요하므로 검색 엔진(OpenSearch 등) 도입도 검토하세요.

## 3단계: 설정과 유지보수

- 통계가 오래되면 계획이 틀어집니다. `pg_stat_user_tables`에서 `last_autoanalyze`를 확인하세요.
- 테이블이 부풀었으면 autovacuum 설정을 조정하세요.
- `shared_buffers`와 `work_mem`이 기본값이면 메모리 크기에 맞게 올리세요.

## 4단계: 그래도 부족하면

1. 읽기 복제본(read replica)으로 조회 부하를 나누세요.
2. 날짜 같은 기준으로 파티셔닝(한 테이블을 내부에서 조각으로 나눔)하세요. 오래된 데이터를 자주 안 읽을 때 효과가 큽니다.
3. 마지막에 샤딩을 검토하세요. 샤딩은 조인, 트랜잭션, 운영 복잡도를 크게 높입니다. 쓰기 처리량이나 총 데이터량이 단일 서버 한계에 닿을 때만 맞습니다.

쿼리 하나와 그 `EXPLAIN (ANALYZE, BUFFERS)` 결과를 보여 주시면 구체적인 인덱스를 제안할 수 있습니다.

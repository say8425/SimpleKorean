사내 API 서버의 인증서를 발급한 인증 기관(CA)을 curl이 신뢰하지 않기 때문에 생기는 오류입니다. 개발과 스테이징 서버가 모두 실패하면 사내 사설 CA가 인증서를 발급했거나, 서버가 중간 인증서를 보내지 않을 가능성이 큽니다.

## 원인 확인

아래 명령으로 서버가 보내는 인증서 체인(chain, 루트 CA까지 이어지는 인증서 목록)을 확인하세요. `api.example.internal`은 실제 호스트로 바꿔야 합니다.

```
openssl s_client -connect api.example.internal:443 -showcerts </dev/null
```

출력에서 다음 두 가지를 봅니다.

- `Verify return code: 20 (unable to get local issuer certificate)`가 나오면 curl이 쓰는 CA 목록에 발급자가 없다는 뜻입니다.
- 인증서가 하나만 보이면 서버가 중간 인증서를 빠뜨린 것입니다. 이 경우 서버 설정을 고쳐야 합니다.

## 해결 방법

사내 루트 CA 인증서(PEM 파일)를 보안팀이나 인프라팀에서 받는 것이 먼저입니다. 그다음 상황에 맞게 하나를 고르세요.

1. 한 번만 쓰면 `--cacert`로 파일을 지정합니다.
   ```
   curl --cacert ~/certs/company-root-ca.pem https://api.example.internal/health
   ```
2. 매번 쓰면 환경 변수를 `~/.zshrc`에 둡니다.
   ```
   export CURL_CA_BUNDLE=$HOME/certs/company-root-ca.pem
   ```
   이 값은 기본 CA 목록을 대체합니다. 공개 사이트에 curl을 보낼 때는 실패할 수 있습니다. 그러면 사내 CA를 기존 목록 파일 뒤에 합쳐서 쓰세요.
3. 시스템 전체에 적용하려면 macOS 키체인(Keychain Access)의 시스템 항목에 인증서를 추가하고 "항상 신뢰"로 설정합니다. 이 방법은 Apple이 제공하는 curl에서만 확실하게 동작합니다. Homebrew로 설치한 curl은 자체 CA 파일을 쓰기 때문에 1번이나 2번이 필요합니다.

서버가 중간 인증서를 보내지 않는 경우에는 서버나 로드 밸런서(load balancer)에 서버 인증서와 중간 인증서를 합친 체인 파일을 설치해야 합니다. 이 경우 클라이언트마다 설정을 바꾸는 것보다 서버를 고치는 쪽이 낫습니다.

## 주의

`curl -k`(또는 `--insecure`)는 인증서 검증을 모두 끕니다. 원인 확인용으로만 쓰고 스크립트나 CI에는 넣지 마세요. 중간자 공격(man-in-the-middle)을 막을 수 없게 됩니다.

사내 프록시가 TLS를 가로채는 환경이면 프록시의 루트 CA가 필요합니다. `openssl s_client` 출력의 발급자(`issuer`)가 사내 프록시 이름이면 이 경우에 해당합니다.

# 토큰 버킷, 쉽게 설명

**비유**: 사용자마다 "토큰이 담긴 양동이"를 하나씩 줍니다.

- 양동이 용량(capacity)이 최대치입니다. 예: 100개
- 요청 1건마다 토큰 1개를 꺼내 씁니다.
- 토큰은 일정 속도로 다시 채워집니다. 분당 100회 제한이면 약 0.0167개/초(=100/60)입니다.
- 양동이가 비어 있으면 요청을 거절합니다(HTTP 429).

**특징**: 양동이가 가득 차 있으면 한꺼번에 최대 100건까지 몰아서 보낼 수 있습니다(버스트 허용). 그 뒤로는 채워지는 속도만큼만 처리됩니다. 즉 "평균은 분당 100회, 순간 버스트는 용량만큼"입니다.

**구현 팁**: 토큰을 타이머로 계속 채울 필요가 없습니다. 사용자별로 `(남은 토큰, 마지막 갱신 시각)`만 저장해 두세요. 요청이 올 때 경과 시간만큼 토큰을 한 번에 계산해 더하면 됩니다. 여러 서버를 쓴다면 Redis에 저장하고, 읽기·계산·쓰기를 Lua 스크립트로 원자적으로 처리하세요. 그렇지 않으면 동시 요청에서 경쟁 상태가 생깁니다.

## 이 경우에 맞는 방법인가요?

**검색 API에는 잘 맞습니다.** 사용자가 잠깐 몰아서 검색해도 괜찮고, 평균만 통제하면 되기 때문입니다.

**로그인 API에는 토큰 버킷 하나만으로는 부족합니다.** 이유는 두 가지입니다.

1. **버스트 허용이 오히려 약점입니다.** 무차별 대입(brute force)이나 크리덴셜 스터핑 공격자는 처음 100번을 즉시 시도할 수 있습니다. 로그인은 분당 100회도 너무 높습니다. 보통 계정당·IP당 분당 5~10회 정도로 훨씬 엄격하게 잡습니다.
2. **"사용자당" 기준이 로그인에는 맞지 않습니다.** 로그인 시도 시점에는 인증된 사용자가 없으니 키를 무엇으로 잡을지가 문제입니다. 공격자는 계정 하나를 여러 IP에서 공격하거나, IP 하나로 여러 계정을 공격할 수 있습니다. 그래서 **IP 기준과 대상 계정(아이디) 기준을 둘 다** 거는 것이 좋습니다.

## 제안

| API | 키 | 방식 |
|---|---|---|
| 검색 | 사용자 ID (비로그인이면 IP) | 토큰 버킷, 용량 100 (또는 버스트를 줄이려 20~30), 분당 100 보충 |
| 로그인 | IP + 시도 대상 계정, 각각 따로 | 훨씬 낮은 한도(예: 분당 5~10), 실패 누적 시 잠금 또는 지연, 필요하면 CAPTCHA |

버스트를 아예 허용하고 싶지 않다면 **슬라이딩 윈도 카운터**나 **리키 버킷**이 대안입니다. "어느 60초 구간에서도 100회 초과 금지"를 엄격하게 지키려면 슬라이딩 윈도가 더 정확합니다. 다만 일반적인 API 보호에는 토큰 버킷이 구현이 단순하고 사용자 경험도 좋아서 충분합니다.

**정리**: 동료의 추천은 검색에는 좋은 선택입니다. 로그인은 알고리즘보다 한도 수치와 키 설계가 더 중요하니, 별도의 더 엄격한 정책을 적용하세요.

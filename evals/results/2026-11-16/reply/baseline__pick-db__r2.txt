샤딩은 거의 마지막 수단입니다. 4천만 행은 Postgres가 단일 노드에서 충분히 감당하는 규모예요. 느린 읽기는 대개 쿼리나 인덱스 문제입니다. 아래 순서로 보시길 권합니다.

## 1. 먼저 측정하기
- **`pg_stat_statements`**로 총 소요시간 기준 상위 쿼리를 찾으세요. 목록·검색 화면이 실제로 날리는 쿼리가 무엇인지 확인하는 단계입니다.
- 느린 쿼리마다 `EXPLAIN (ANALYZE, BUFFERS)`를 실행하세요. 봐야 할 것은 이 세 가지입니다.
  - Seq Scan이 나오는지
  - 예상 행 수와 실제 행 수가 크게 다른지
  - 디스크 읽기(`read`)가 많은지
- `auto_explain`과 `log_min_duration_statement`를 켜 두면 운영 중에 느린 쿼리를 잡을 수 있습니다.

## 2. 목록 화면에서 흔한 원인
- **OFFSET 페이지네이션**: `OFFSET 100000`은 앞의 10만 행을 읽고 버립니다. **키셋(커서) 페이지네이션**(`WHERE (created_at, id) < (?, ?) ORDER BY created_at DESC, id DESC LIMIT 20`)으로 바꾸세요.
- **`COUNT(*)`로 전체 건수 표시**: 4천만 행에서는 비쌉니다. 근사치(통계 기반)를 쓰거나, 상한을 두거나("10,000+"), 전체 건수를 아예 없애는 쪽을 검토하세요.
- **정렬용 인덱스 부재**: `WHERE` 조건과 `ORDER BY`에 맞는 복합 인덱스가 없으면 매번 정렬합니다. 자주 쓰는 필터에는 부분 인덱스(partial index)도 유효합니다.
- **`SELECT *`**: 넓은 컬럼(JSON, 텍스트)을 불필요하게 읽습니다. 필요한 컬럼만 선택하면 index-only scan도 가능해집니다.

## 3. 검색 화면에서 흔한 원인
- `LIKE '%키워드%'`나 `ILIKE`는 일반 B-tree 인덱스를 못 탑니다. 선택지는 다음과 같습니다.
  - **`pg_trgm` + GIN/GiST 인덱스**: 부분 문자열 검색용
  - **전문 검색(`tsvector` + GIN)**: 단어 기반 검색용
- 한국어는 형태소 분석이 필요해서 기본 `tsvector`만으로는 부족할 수 있습니다. 이 경우 `pg_trgm`이 현실적인 출발점이고, 검색 요구가 크면 Elasticsearch/OpenSearch 같은 별도 검색 엔진을 두는 것이 맞습니다.
- 함수가 씌워진 컬럼(`lower(col)` 등)에는 표현식 인덱스가 필요합니다.

## 4. 테이블과 DB 상태
- **Bloat / vacuum**: `pg_stat_user_tables`에서 dead tuple 비율과 `last_autovacuum`을 확인하세요. 업데이트·삭제가 많다면 autovacuum 설정을 조정합니다.
- **`ANALYZE`**: 통계가 오래되면 플래너가 잘못된 계획을 고릅니다.
- **캐시 적중률**: 자주 쓰는 데이터와 인덱스가 `shared_buffers`와 OS 캐시에 들어가는지 확인하세요. 안 들어간다면 메모리를 늘리는 쪽이 샤딩보다 훨씬 쌉니다.
- 인덱스 크기와 미사용 인덱스를 점검하세요. 인덱스가 너무 많으면 쓰기가 느려집니다.

## 5. 그래도 부족할 때, 샤딩 전 단계
1. **읽기 복제본(read replica)**: 목록·검색 같은 읽기 트래픽을 분리합니다.
2. **캐싱**: 자주 보는 목록 결과를 Redis 등에 두세요.
3. **파티셔닝**: 시간이나 테넌트 기준으로 테이블을 나눕니다. 한 DB 안에서 하는 것이라 샤딩보다 훨씬 단순합니다. 쿼리가 파티션 키로 필터링할 때만 효과가 있다는 점은 주의하세요.
4. **검색 엔진 분리**: 검색 부하를 Postgres 밖으로 옮깁니다.
5. 오래된 데이터를 아카이빙해 활성 데이터셋을 줄입니다.

## 샤딩은 언제?
쓰기 처리량이 단일 노드 한계에 닿았거나, 데이터가 노드 하나의 저장·메모리 한계를 넘는데 위 방법으로 해결되지 않을 때입니다. 샤딩은 조인, 트랜잭션, 운영 복잡도를 크게 높이기 때문에 앞 단계를 다 해본 뒤에 고려해도 늦지 않습니다.

## 다음 단계 제안
가장 빠른 길은 느린 쿼리 2~3개의 `EXPLAIN (ANALYZE, BUFFERS)` 결과와 테이블 스키마(인덱스 포함)를 공유해 주시는 겁니다. 그러면 원인과 구체적인 인덱스·쿼리 수정안을 짚어 드릴 수 있어요.

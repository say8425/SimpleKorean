## 토큰 버킷, 쉽게 설명

**비유:** 사용자마다 "토큰이 담긴 양동이"가 하나씩 있다고 생각하세요.

- 양동이는 최대 N개(용량)까지 담을 수 있어요.
- 일정 속도로 토큰이 자동으로 채워져요. (예: 분당 100개 → 약 0.6초에 1개)
- 요청 하나가 올 때마다 토큰 1개를 꺼내요.
- 토큰이 없으면 요청을 거절해요(HTTP 429).

용량이 100이면, 한동안 쉬던 사용자는 100번을 한꺼번에 보낼 수 있어요(버스트 허용). 그 뒤로는 채워지는 속도만큼만 보낼 수 있어요.

**구현 요점**
- 저장하는 값은 사용자별로 `남은 토큰 수`와 `마지막 갱신 시각` 두 개뿐이에요.
- 요청이 올 때 `경과 시간 × 충전 속도`만큼 토큰을 더하고(용량 상한까지), 1개를 차감해요. 타이머로 채우는 게 아니라 요청 시점에 계산해요.
- 서버가 여러 대면 Redis에 저장하고 Lua 스크립트로 "읽기-계산-쓰기"를 원자적으로 처리해야 해요. 안 그러면 동시 요청에서 한도가 뚫려요.

## 맞는 방법인가요?

**검색 API에는 잘 맞아요.** 짧은 버스트를 허용하면서 평균 속도를 제한하는 데 적합하고, 구현도 가볍고 메모리도 적게 써요.

**로그인 API에는 토큰 버킷만으로는 부족해요.** 이유는 이래요.

- 분당 100회는 로그인에는 너무 느슨해요. 한 계정에 비밀번호를 대입하는 공격이라면 분당 100번도 많아요.
- 사용자 기준 제한은 로그인 전에는 "사용자"를 특정할 수 없어서 우회하기 쉬워요. 공격자가 여러 계정이나 IP를 돌려 쓰면 소용없어요.

**권장 구성**

| API | 제한 기준 | 방식 |
|---|---|---|
| 검색 | 사용자(ID 또는 토큰)별 | 토큰 버킷, 분당 100 |
| 로그인 | IP별 + 대상 계정별 | 훨씬 낮은 한도(예: 분당 5~10회) + 연속 실패 시 잠금·지연·CAPTCHA |

**참고할 점**
- "정확히 분당 100회"를 엄격하게 지켜야 한다면 슬라이딩 윈도우가 더 맞아요. 토큰 버킷은 버스트 때문에 짧은 시간에 100회를 넘게 보낼 수 있는 구간이 생겨요(용량을 낮추면 완화돼요).
- 응답에 `429`와 `Retry-After` 헤더를 넣어 주세요.
- 이미 API 게이트웨이(Kong, NGINX, AWS API Gateway 등)를 쓰신다면 내장 기능이 있는지 먼저 확인해 보세요.

원하시면 Redis + Lua로 만든 구현 예시를 써 드릴게요. 쓰시는 언어와 스택을 알려 주세요.

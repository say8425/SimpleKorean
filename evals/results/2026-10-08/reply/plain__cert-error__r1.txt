curl이 서버 인증서를 발행한 인증 기관(CA)을 자신의 신뢰 목록에서 찾지 못했다는 뜻입니다. 사내 API는 보통 사내 루트 CA가 서명한 인증서를 쓰는데, 공인 CA 목록에는 이 CA가 없습니다. 회사 프록시가 TLS 통신을 가로채 자체 인증서로 바꿀 때도 같은 오류가 납니다. 서버가 중간 인증서(intermediate)를 보내지 않을 때도 발생할 수 있습니다.

먼저 서버가 보내는 인증서 체인을 확인합니다. 아래 명령에서 호스트는 실제 사내 API 호스트로 바꿔야 합니다.

```
openssl s_client -connect api.example.internal:443 -showcerts </dev/null
```

출력에 사내 CA 이름이 보이면 해당 루트 CA 인증서(PEM 파일)를 IT 부서나 사내 위키에서 받습니다. 그 파일을 `--cacert`로 지정하면 요청이 통과합니다.

```
curl --cacert /path/to/company-root-ca.pem https://api.example.internal/v1/health
```

매번 지정하기 번거로우면 `CURL_CA_BUNDLE` 환경 변수에 같은 파일 경로를 넣습니다. 이 변수는 기본 신뢰 목록을 대체하기 때문에 공인 사이트 요청이 실패할 수 있습니다. 이 경우 시스템 CA 번들 뒤에 사내 CA를 이어 붙인 파일을 만들어 지정해야 합니다.

macOS에서는 키체인에 CA를 추가해도 해결되지 않을 수 있습니다. Homebrew로 설치한 curl은 키체인 대신 자체 CA 번들을 읽기 때문입니다.

`curl -k`는 인증서 검증을 끄기 때문에 통신 내용이 노출되거나 변조될 수 있습니다. 원인을 진단할 때만 잠깐 쓰고, 스크립트나 운영 환경에는 넣으면 안 됩니다.

체인에 사내 CA가 보이지 않고 프록시 회사 이름이 보이면 프록시의 루트 인증서를 받아 같은 방법으로 지정하면 됩니다. 서버 체인에 중간 인증서가 빠졌다면 서버 담당자가 인증서 설정을 고쳐야 합니다.

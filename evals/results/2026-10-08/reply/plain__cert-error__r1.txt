사내 API 서버의 인증서를 발급한 인증기관(CA, 인증서에 서명하는 기관)을 curl이 신뢰하지 못하는 오류입니다. 사내 API는 보통 회사가 직접 운영하는 사설 CA로 서명하기 때문에 curl의 기본 신뢰 목록에 그 CA가 없습니다.

원인은 세 가지로 나뉩니다. 첫째, 서버 인증서가 사설 루트 CA로 서명되었습니다. 둘째, 서버가 중간 인증서를 함께 보내지 않아 인증 경로가 끊깁니다. 셋째, 회사 프록시가 HTTPS를 가로채 자체 인증서로 다시 서명합니다. 어느 경우인지 먼저 확인하세요. 아래 명령은 서버가 보내는 인증서 체인을 출력합니다. `api.example.internal`은 실제 호스트로 바꾸세요.

```
openssl s_client -connect api.example.internal:443 -showcerts </dev/null
```

출력의 `issuer` 줄이 사내 CA나 프록시 이름이면 첫째 또는 셋째 원인입니다. 체인에 인증서가 하나뿐이고 `verify error` 메시지가 나오면 둘째 원인입니다. 둘째 원인은 서버 관리자가 중간 인증서를 서버 설정에 추가해야 고쳐집니다.

첫째와 셋째 원인은 사내 루트 CA 인증서(PEM 형식)를 받아 curl에 지정하면 고쳐집니다. 인증서 파일은 보안팀이나 사내 위키에서 받을 수 있습니다. 경로는 예시입니다.

```
curl --cacert ~/certs/company-root-ca.pem https://api.example.internal/health
```

매번 옵션을 쓰기 싫으면 환경 변수를 설정하세요. 이 값은 현재 셸에만 적용됩니다. 계속 쓰려면 `~/.zshrc`에 추가해야 합니다.

```
export CURL_CA_BUNDLE=~/certs/company-root-ca.pem
```

`-k`나 `--insecure` 옵션은 쓰지 마세요. 이 옵션은 인증서 검증을 끄기 때문에 중간자 공격(통신 중간에서 내용을 가로채는 공격)을 막지 못합니다. 임시 확인 용도로만 쓰고 스크립트에 남기지 마세요.

같은 오류가 Python이나 Node.js에서도 나면 각자의 신뢰 목록을 쓰기 때문입니다. 이 경우 `REQUESTS_CA_BUNDLE`이나 `NODE_EXTRA_CA_CERTS` 같은 환경 변수에 같은 PEM 파일을 지정해야 합니다.

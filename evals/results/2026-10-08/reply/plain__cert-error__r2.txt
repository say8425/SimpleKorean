curl이 서버 인증서를 발급한 인증 기관(CA, 인증서에 서명하는 기관)을 신뢰 목록에서 찾지 못해서 나는 오류입니다. 사내 API는 보통 사내 사설 CA가 서명하거나, 회사 프록시가 TLS 트래픽을 가로채 인증서를 다시 서명합니다. 두 경우 모두 curl의 기본 CA 목록에 그 CA가 없습니다. 서버가 중간 인증서를 보내지 않는 설정 오류도 같은 오류를 냅니다.

먼저 서버가 보내는 인증서 체인을 확인하세요. `api.example.com`은 실제 호스트로 바꾸세요.

```
openssl s_client -connect api.example.com:443 -showcerts </dev/null
```

출력의 `issuer` 줄이 사내 CA 이름이면 사설 CA 문제입니다. 체인에 인증서가 하나뿐이고 `unable to verify the first certificate`가 보이면 서버에 중간 인증서가 빠진 것입니다. 이 경우 API 담당 팀에 체인 구성을 고쳐 달라고 요청해야 합니다.

사설 CA 문제라면 보안팀이나 IT 부서에서 사내 루트 CA 인증서(PEM 파일)를 받으세요. 그다음 curl에 그 파일을 직접 지정하세요.

```
curl --cacert /path/to/company-root-ca.pem https://api.example.com/health
```

매번 지정하기 번거로우면 셸 설정에 환경 변수를 추가하세요. 이 변수는 시스템 CA 목록을 대체하므로 공개 사이트 요청은 실패할 수 있습니다. 그때는 공개 CA 번들 뒤에 사내 CA를 이어 붙인 파일을 지정해야 합니다.

```
export CURL_CA_BUNDLE=/path/to/company-root-ca.pem
```

macOS에서 `/usr/bin/curl`은 시스템 키체인을 참조하지만, Homebrew로 설치한 curl은 자체 CA 번들을 씁니다. 키체인에 사내 CA를 등록했는데도 오류가 나면 `which curl`로 어느 curl을 쓰는지 확인하세요.

`curl -k`(또는 `--insecure`)로 오류를 우회할 수 있지만 운영 환경과 인증 정보를 보내는 요청에는 쓰면 안 됩니다. 이 옵션은 서버 검증을 모두 끄기 때문에 중간자 공격(통신 중간에서 내용을 가로채는 공격)에 노출됩니다. 원인을 가리는 임시 확인용으로만 쓰세요.

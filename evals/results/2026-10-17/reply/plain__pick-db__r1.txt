샤딩(sharding, 데이터를 여러 서버에 나눠 저장하는 방식)은 마지막 수단입니다. 4천만 행은 Postgres 한 대가 충분히 감당하는 규모이고, 읽기가 느린 원인은 대개 인덱스, 쿼리, 메모리에 있습니다. 아래 순서로 확인하세요.

1. 느린 쿼리를 찾으세요. `pg_stat_statements` 확장을 켜면 총 소요 시간이 큰 쿼리를 볼 수 있습니다.
2. 그 쿼리에 실행 계획을 확인하세요.
3. 계획에 `Seq Scan`이 보이면 해당 칼럼에 인덱스를 추가하세요.
4. 테이블 통계를 갱신하고 bloat(삭제된 행이 차지한 낭비 공간)를 확인하세요.
5. 서버 메모리 설정을 확인하세요.

```sql
-- 3번: 운영 중인 테이블에는 CONCURRENTLY를 붙여 쓰기 잠금을 피합니다.
-- (items, user_id는 예시 이름입니다.)
EXPLAIN (ANALYZE, BUFFERS) SELECT ... ;
CREATE INDEX CONCURRENTLY idx_items_user_id ON items (user_id);
ANALYZE items;
```

`EXPLAIN ANALYZE`는 쿼리를 실제로 실행합니다. `UPDATE`나 `DELETE`에 쓰면 데이터가 바뀌므로 트랜잭션 안에서 실행하고 롤백해야 합니다.

4번에서는 `pg_stat_user_tables`의 `n_dead_tup`과 autovacuum 마지막 실행 시각을 보세요. 5번에서는 `shared_buffers`와 `effective_cache_size`가 서버 메모리에 맞는지 보세요. 자주 읽는 데이터가 메모리에 들어가지 않으면 디스크 읽기가 늘어 느려집니다.

여기까지 해도 느리면 샤딩 전에 다음 방법이 있습니다.

- 읽기 복제본(read replica)으로 읽기 부하를 분산합니다.
- 날짜 같은 기준으로 테이블을 파티셔닝(partitioning, 한 테이블을 조각으로 나눔)합니다. 오래된 데이터는 스캔에서 빠집니다.
- 자주 읽는 결과를 Redis 같은 캐시에 둡니다.

샤딩은 쓰기 처리량이나 총 데이터 크기가 서버 한 대의 한계를 넘을 때 고려합니다. 조인과 트랜잭션이 복잡해지고 운영 비용이 크게 늘기 때문에 읽기 문제만으로는 맞지 않습니다.

느린 쿼리와 `EXPLAIN (ANALYZE, BUFFERS)` 결과를 보내면 원인을 더 좁힐 수 있습니다.

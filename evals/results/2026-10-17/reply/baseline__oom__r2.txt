# OOMKilled 원인과 해결

## 무슨 일이 일어나는가

컨테이너의 메모리 사용량이 `resources.limits.memory`를 넘으면 리눅스 커널의 cgroup OOM killer가 프로세스를 강제 종료합니다. 종료 코드는 **137**(SIGKILL)입니다. 그러면 kubelet이 `restartPolicy`에 따라 컨테이너를 재시작합니다. 같은 이유로 계속 죽으면 재시작 간격이 점점 길어지고, 상태가 `CrashLoopBackOff`로 보입니다.

참고로 이 OOM은 파드가 속한 **노드**의 메모리가 부족할 때 일어나는 축출(Evicted)과는 다릅니다. OOMKilled는 해당 컨테이너가 자기 limit을 넘겼다는 뜻입니다.

## 먼저 확인할 것

```bash
# 마지막 종료 사유 확인 (Reason: OOMKilled, Exit Code: 137)
kubectl describe pod <pod> | grep -A5 "Last State"

# 현재 사용량 vs limit
kubectl top pod <pod> --containers
kubectl get pod <pod> -o jsonpath='{.spec.containers[*].resources}'

# 죽기 직전 로그
kubectl logs <pod> --previous
```

Prometheus를 쓴다면 `container_memory_working_set_bytes`의 추이도 보세요. 우상향이면 누수이고, 시작 직후 급등이면 limit이 너무 낮은 것입니다.

## 원인별 조치

**1. limit이 실제 필요량보다 낮은 경우** (가장 흔함)
```yaml
resources:
  requests:
    memory: "512Mi"
  limits:
    memory: "1Gi"   # 정상 피크 사용량의 1.2~1.5배 정도
```
`requests`는 평균 사용량에, `limits`는 피크에 맞춥니다. 안정성이 중요하면 requests와 limits를 같게 두어 QoS를 Guaranteed로 만드는 것도 방법입니다.

**2. 애플리케이션 메모리 누수**
limit만 올리면 죽는 시점이 늦춰질 뿐입니다. 힙 덤프나 프로파일링으로 원인을 찾아야 합니다.

**3. 런타임이 컨테이너 limit을 모르는 경우**
- **JVM**: 힙이 limit보다 커지면 죽습니다. 힙 외 메모리(메타스페이스, 스레드 스택, 다이렉트 버퍼)도 고려해야 합니다.
  `-XX:MaxRAMPercentage=70.0` 정도로 설정하세요(JDK 10 이상은 컨테이너를 인식합니다).
- **Node.js**: `--max-old-space-size`를 limit의 약 75% 이하로 설정합니다.
- **Go**: `GOMEMLIMIT`을 limit의 90% 정도로 설정합니다.

**4. 일시적 스파이크**
대용량 파일 처리, 대량 쿼리, 캐시 워밍 같은 작업은 스트리밍이나 배치 크기 조정으로 줄입니다. 부하에 따라 늘어나는 구조라면 HPA로 파드 수를 늘리는 것도 방법입니다.

**5. 사이드카나 tmpfs**
`emptyDir`에 `medium: Memory`를 쓰면 그 용량도 컨테이너 메모리로 계산됩니다. 사이드카(istio-proxy 등)가 따로 죽는 경우도 있으니 컨테이너별로 확인하세요.

## 권장 순서

1. `describe`로 어느 컨테이너가 OOMKilled인지 확인
2. 메모리 추이를 보고 누수인지 limit 부족인지 판단
3. limit 부족이면 limit을 올리고, 런타임 메모리 옵션을 limit에 맞춤
4. 누수이면 프로파일링으로 수정
5. 장기적으로는 VPA(추천 모드)로 적정값을 산출

사용 중인 언어와 런타임, `kubectl describe pod` 출력, 메모리 추이를 알려주시면 더 구체적인 값을 제안해 드리겠습니다.

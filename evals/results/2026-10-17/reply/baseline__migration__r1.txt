**백필(backfill)**은 이미 있는 기존 행들의 새 컬럼에 값을 채워 넣는 작업입니다.

## 왜 멈췄나

`ADD COLUMN ... NOT NULL`을 하면 DB는 기존 모든 행이 그 컬럼에 값을 가져야 한다고 보장해야 합니다. 20GB 테이블이면 다음 중 하나가 일어납니다.

- 기본값이 없으면: 기존 행이 NULL이라 제약 위반으로 실패합니다.
- 기본값이 있어도 DB/버전에 따라 테이블 전체를 다시 쓰거나 스캔합니다. 이때 `ACCESS EXCLUSIVE` 락(MySQL이면 metadata lock)을 잡고 있어서 다른 쿼리가 줄줄이 대기합니다. 지금 멈춘 것처럼 보이는 이유가 이것일 가능성이 큽니다.

PostgreSQL 11+는 상수 기본값이면 테이블을 다시 쓰지 않아 빠릅니다. MySQL 8.0도 `ALGORITHM=INSTANT`가 가능한 경우가 있습니다. 어떤 DB와 버전인지에 따라 상황이 달라집니다.

## 먼저 할 일 (지금 멈춘 상태)

1. 마이그레이션을 중단합니다. 락을 쥔 세션이나 대기 중인 쿼리가 서비스에 영향을 주고 있을 수 있습니다.
   - PostgreSQL: `pg_stat_activity`에서 확인하고 `pg_cancel_backend(pid)`를 씁니다.
   - MySQL: `SHOW PROCESSLIST`로 확인하고 `KILL <id>`를 씁니다.
2. 롤백이 끝나 테이블이 정상인지 확인합니다. 롤백도 오래 걸릴 수 있습니다.

## 안전한 방식 (3단계 분리)

1. **컬럼을 nullable로 추가합니다.** 필요하면 기본값도 함께 줍니다. 메타데이터만 바뀌어서 거의 즉시 끝납니다.
   ```sql
   ALTER TABLE t ADD COLUMN new_col INT;
   ```
2. **배치로 백필합니다.** 예를 들어 1만~5만 행씩 PK 범위로 나눠 UPDATE하고, 배치 사이에 잠깐 쉽니다. 한 트랜잭션으로 20GB를 건드리면 락, 복제 지연, WAL/undo 폭증이 생깁니다.
   ```sql
   UPDATE t SET new_col = <값>
   WHERE id BETWEEN :start AND :end AND new_col IS NULL;
   ```
   그 사이 들어오는 신규 행은 애플리케이션이 새 컬럼에 값을 쓰도록 먼저 배포해 둬야 합니다.
3. **NOT NULL 제약을 건니다.**
   - PostgreSQL: 먼저 `ADD CONSTRAINT ... CHECK (new_col IS NOT NULL) NOT VALID`를 추가합니다. 그다음 `VALIDATE CONSTRAINT`를 실행하면 쓰기를 막지 않고 검증됩니다. 그 후 `SET NOT NULL`을 하면 검증된 CHECK 덕에 스캔 없이 끝납니다.
   - MySQL: 온라인 DDL이나 `gh-ost`/`pt-online-schema-change`를 씁니다.

## 운영 팁

- 마이그레이션에 `lock_timeout`을 걸어 두면 락을 못 잡을 때 서비스를 막지 않고 빨리 실패합니다.
- 백필은 트래픽이 적은 시간에 돌리고, 복제 지연을 모니터링하며 배치 크기를 조절합니다.
- 백필 스크립트는 재실행해도 안전하게(`WHERE new_col IS NULL`) 작성합니다.

DB 종류와 버전(PostgreSQL/MySQL 등), 추가한 컬럼의 기본값 유무를 알려주시면 그에 맞춰 구체적인 SQL과 배치 스크립트를 작성해 드리겠습니다.

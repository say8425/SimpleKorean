디스크는 보통 네 곳에서 찬다. 데이터 파일(테이블과 인덱스), WAL(변경 기록 파일), 로그, 임시 파일입니다. 아래 순서로 어디가 큰지 먼저 확인하세요.

## 1. 서버에서 큰 디렉터리 찾기

데이터 디렉터리 경로는 `SHOW data_directory;`로 확인합니다. 아래 예시는 `/var/lib/postgresql/data`를 씁니다. 셸에서 실행합니다.

```
df -h
sudo du -xh --max-depth=1 /var/lib/postgresql/data | sort -h | tail
sudo du -sh /var/lib/postgresql/data/pg_wal
sudo du -sh /var/log/postgresql
```

`base`가 크면 데이터 파일이 원인입니다. `pg_wal`이 크면 WAL이 쌓인 것입니다. 로그 디렉터리도 같이 확인해야 합니다.

## 2. 데이터베이스 안에서 큰 객체 찾기

```sql
SELECT datname, pg_size_pretty(pg_database_size(datname))
FROM pg_database ORDER BY pg_database_size(datname) DESC;

SELECT relname, pg_size_pretty(pg_total_relation_size(oid)) AS total,
       pg_size_pretty(pg_relation_size(oid)) AS table_only
FROM pg_class
WHERE relkind = 'r'
ORDER BY pg_total_relation_size(oid) DESC
LIMIT 20;
```

total과 table_only 차이가 크면 인덱스가 큰 것입니다. 부풀어 오른 테이블(bloat, 지운 행의 빈 공간이 남은 상태)은 다음 쿼리로 찾습니다.

```sql
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC LIMIT 20;
```

## 3. WAL이 쌓이는 원인 확인

비활성 복제 슬롯(replication slot, 복제본이 읽을 WAL을 붙잡아 두는 장치)이 가장 흔한 원인입니다. 아카이브 실패도 원인이 됩니다.

```sql
SELECT slot_name, active, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
FROM pg_replication_slots;

SELECT archived_count, failed_count, last_failed_wal FROM pg_stat_archiver;
```

## 4. 공간을 비우는 방법

가장 안전한 것부터 나열합니다.

- 오래된 서버 로그, 덤프 파일, 백업 파일을 지웁니다. 이 파일들은 Postgres 밖에 있어서 위험이 가장 작습니다.
- 더 쓰지 않는 복제 슬롯은 `SELECT pg_drop_replication_slot('슬롯이름');`으로 지웁니다. 복제본이 아직 쓰는 슬롯이면 지우면 안 됩니다. 지우면 그 복제본을 다시 만들어야 합니다.
- 아카이브 실패가 원인이면 `archive_command` 대상(저장소 연결, 권한, 용량)을 고칩니다. 고치면 WAL이 스스로 정리됩니다.
- 오래된 데이터는 `DELETE` 대신 파티션 삭제(`DROP TABLE`)나 `TRUNCATE`로 지웁니다. 이 두 방법은 공간을 OS에 바로 돌려줍니다.
- 쓰지 않는 인덱스는 `pg_stat_user_indexes`에서 `idx_scan = 0`인 것을 찾아 지웁니다.
- bloat가 큰 테이블은 `pg_repack`으로 줄입니다. 일반 `VACUUM`은 공간을 재사용하게 만들 뿐이고, OS에 거의 돌려주지 않습니다.

## 주의

- `pg_wal` 안의 파일을 직접 지우면 안 됩니다. 서버가 시작되지 않거나 데이터가 깨질 수 있습니다.
- `VACUUM FULL`과 `pg_repack`은 테이블 크기만큼 빈 공간이 더 필요합니다. 디스크가 거의 찼을 때 실행하면 실패합니다. 먼저 위 방법으로 여유를 만드세요.
- `VACUUM FULL`은 실행하는 동안 테이블을 잠급니다. 서비스 시간에는 피해야 합니다.
- 디스크가 100%에 닿으면 Postgres가 멈춥니다. 급하면 볼륨을 먼저 늘리고 원인은 그다음에 찾아도 됩니다.

확인한 결과(`du` 출력이나 큰 테이블 목록)를 보내 주시면 원인에 맞는 조치를 좁혀 드릴 수 있습니다.

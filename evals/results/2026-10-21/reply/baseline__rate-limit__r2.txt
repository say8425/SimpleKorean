## 토큰 버킷, 쉽게 설명

**비유**: 사용자마다 "토큰이 담기는 양동이"가 하나씩 있다고 생각하세요.

- 양동이에는 최대 100개까지 토큰이 담깁니다(용량).
- 시간이 지나면 일정 속도로 토큰이 채워집니다(분당 100개 ≈ 0.6초에 1개).
- 요청 1건마다 토큰 1개를 꺼내 씁니다.
- 양동이가 비어 있으면 요청을 거절합니다(HTTP 429).

그래서 평소에는 분당 100회 평균을 지키면서, 한동안 쉬었다가 갑자기 몰려오는 짧은 버스트(최대 100건)도 허용합니다.

**구현 팁**: 토큰을 실제로 채우는 타이머는 필요 없습니다. 사용자별로 `(남은 토큰, 마지막 갱신 시각)`만 저장해 두고, 요청이 올 때 `경과 시간 × 충전 속도`만큼 더해서 계산하면 됩니다. 여러 서버라면 Redis에 저장하고 Lua 스크립트로 읽기·계산·쓰기를 원자적으로 처리하세요.

## 맞는 방법인가요?

**검색 API에는 잘 맞습니다.** 사용자가 잠깐 몰아서 검색해도 자연스럽게 허용하고, 지속적인 남용만 막아 주기 때문입니다.

**로그인 API에는 이것만으로는 부족합니다.** 이유는 다음과 같습니다.

1. **공격 대상이 다릅니다.** 로그인의 위험은 무차별 대입과 크리덴셜 스터핑입니다. 분당 100회는 비밀번호 시도 횟수로는 너무 많습니다.
2. **"사용자당" 기준이 로그인에는 맞지 않습니다.** 로그인 시점에는 사용자가 아직 식별되지 않았습니다. 공격자는 계정 하나에 여러 IP로 시도하거나, IP 하나로 여러 계정을 시도합니다. 그래서 IP 기준과 계정(아이디) 기준을 함께 걸어야 합니다.
3. **버스트 허용이 오히려 불리합니다.** 토큰 버킷은 용량만큼 한꺼번에 허용하므로, 로그인에서는 용량을 작게 잡아야 합니다.

## 권장안

| API | 방식 | 예시 |
|---|---|---|
| 검색 | 사용자별 토큰 버킷 | 용량 100, 분당 100 충전 |
| 로그인 | 계정별 + IP별 별도 제한 (작은 버킷 또는 슬라이딩 윈도우) | 계정당 5~10회/분, IP당 20회/분. 실패가 누적되면 지연이나 CAPTCHA, 일시 잠금 추가 |

## 참고

- **엄격한 "정확히 분당 100회"가 필요하면** 슬라이딩 윈도우 카운터가 더 직관적입니다. 토큰 버킷은 1분 구간 안에 최대 약 200회(버킷 100 + 충전 100)까지 통과할 수 있기 때문입니다. 용량을 줄이면 이 문제를 완화할 수 있습니다.
- 거절할 때는 `429`와 함께 `Retry-After` 헤더를 내려 주세요.
- 비로그인 요청은 IP 기준으로 제한하되, 회사 NAT나 프록시 뒤에서는 여러 사용자가 한 IP를 공유한다는 점을 고려하세요.

스택(Redis 사용 여부, API 게이트웨이 유무 등)을 알려 주시면 구체적인 구현 예시도 드릴 수 있습니다.

OOMKilled는 컨테이너가 메모리 limit(컨테이너가 쓸 수 있는 메모리 상한)을 넘어서 커널이 프로세스를 강제로 종료했다는 뜻입니다. 쿠버네티스는 종료된 컨테이너를 재시작하고, 반복되면 CrashLoopBackOff 상태가 됩니다. API와 워커가 모두 죽으면 공통 원인이 있을 가능성이 큽니다.

## 무슨 일이 일어나는가

1. 컨테이너의 메모리 사용량이 `resources.limits.memory`에 닿습니다.
2. 커널의 OOM killer가 프로세스에 SIGKILL을 보냅니다.
3. kubelet이 종료 사유를 `OOMKilled`, 종료 코드를 137로 기록합니다.
4. kubelet이 컨테이너를 재시작하고, 재시작 간격은 점점 길어집니다.

## 먼저 확인할 것

사유가 limit 초과인지 먼저 확인하세요.

```
kubectl describe pod <파드> -n <네임스페이스>
```

`Last State: Terminated`의 `Reason: OOMKilled`와 `Exit Code: 137`을 찾으세요. 현재 사용량은 아래 명령으로 볼 수 있습니다. 이 명령은 metrics-server가 설치되어 있어야 합니다.

```
kubectl top pod <파드> -n <네임스페이스> --containers
```

사용량 그래프의 모양이 원인을 가려 줍니다.

- 시간이 지날수록 계속 오르면 메모리 누수입니다.
- 요청이나 작업이 몰릴 때 급등하면 동시 처리량이 limit에 비해 큰 것입니다.
- 시작 직후 바로 죽으면 limit이 기본 적재량보다 작은 것입니다.

## 둘 다 죽는 이유로 의심할 것

- 최근 배포에서 limit을 낮췄거나, 두 워크로드가 같은 Helm 값이나 템플릿을 씁니다.
- 둘이 같은 라이브러리를 쓰고, 새 버전에 누수나 캐시 증가가 있습니다.
- 런타임이 컨테이너 limit을 모릅니다. 예를 들어 JVM 힙, Node.js의 old-space, Go의 GC 목표가 노드 전체 메모리를 기준으로 잡히면 limit을 넘습니다.
- 같은 노드의 메모리가 부족합니다. 이 경우 `kubectl describe node`에서 `MemoryPressure`를 확인하세요. 노드 압박으로 쫓겨난 파드는 OOMKilled가 아니라 `Evicted`로 표시됩니다.

## 바꿔야 할 것

1. limit을 실측 최대 사용량의 1.2~1.5배로 올리세요. request는 평상시 사용량에, limit은 최대치에 맞추세요.
2. 런타임 메모리 설정을 limit의 70~80%로 제한하세요. 예를 들어 JVM은 `-XX:MaxRAMPercentage=75`, Node.js는 `--max-old-space-size`, Go는 `GOMEMLIMIT`을 씁니다.
3. 워커는 동시 처리 수, 배치 크기, 큐에서 한 번에 가져오는 메시지 수를 줄이세요. 큰 파일이나 결과 전체를 메모리에 올리지 말고 스트리밍으로 처리하세요.
4. 사용량이 계속 오르면 limit만 올려서는 해결되지 않습니다. 힙 프로파일을 떠서 누수 지점을 고쳐야 합니다.
5. 반복되면 메모리 사용량과 재시작 횟수에 알림을 걸어 두세요.

정확한 값을 정하려면 세 가지가 필요합니다. 언어와 런타임, 현재 `resources` 설정, `kubectl describe pod` 출력의 `Last State` 부분입니다.

클러스터나 매니페스트는 아직 보지 못했습니다. 아래는 OOMKilled의 일반적인 원리와 확인·수정 순서입니다.

## 무슨 일이 일어나는가

OOMKilled는 컨테이너가 메모리 limit을 넘어서 리눅스 커널의 cgroup OOM killer가 프로세스를 SIGKILL(exit code 137)로 죽였다는 뜻입니다. kubelet은 `restartPolicy`에 따라 컨테이너를 다시 띄웁니다. 같은 이유로 계속 죽으면 `CrashLoopBackOff`가 됩니다.

API와 워커가 둘 다 죽는다면 원인은 다음 중 하나일 가능성이 큽니다.

1. **limit이 너무 낮음**: 실제 사용량이 정상적으로 limit보다 큽니다.
2. **런타임이 limit을 모름**
   - JVM은 `-Xmx`가 limit보다 크거나, heap 외 영역(metaspace, 스레드 스택, direct buffer)을 계산하지 않은 경우입니다.
   - Node는 `--max-old-space-size`가 기본값이라 limit과 맞지 않는 경우입니다.
   - Python이나 Go는 워커 프로세스 수와 `GOMEMLIMIT` 설정이 limit과 맞지 않는 경우입니다.
3. **메모리 누수나 무제한 증가**: 큐에서 큰 배치를 읽거나, 캐시에 상한이 없거나, 큰 응답을 통째로 메모리에 올리는 경우입니다.
4. **동시성 과다**: 워커의 concurrency나 API의 요청 동시 처리 수가 메모리 예산보다 큽니다.
5. **공통 변경점**: 둘이 같은 시점에 시작됐다면 최근 배포, 공통 라이브러리 업데이트, 공유 설정(Helm values, 공통 limit 기본값)을 의심해 보세요.

## 확인 방법

```bash
# 종료 사유와 시점 확인 (Last State: Terminated, Reason: OOMKilled)
kubectl describe pod <pod> -n <ns>

# 현재 사용량 vs limit
kubectl top pod -n <ns> --containers
kubectl get pod <pod> -n <ns> -o jsonpath='{.spec.containers[*].resources}'

# 직전 컨테이너 로그
kubectl logs <pod> -n <ns> --previous

# 노드 쪽 OOM 로그 (노드 메모리 압박인지 컨테이너 limit인지 구분)
kubectl describe node <node> | grep -A5 -i "pressure\|oom"
```

Prometheus를 쓰신다면 `container_memory_working_set_bytes`의 추이를 보세요. 시간이 지날수록 계속 오르면 누수, 시작 직후 급등하면 limit 부족이나 배치 크기 문제입니다.

## 무엇을 바꿔야 하는가

1. **원인 구분 먼저**: 사용량이 완만히 오르다 죽으면 누수이니 코드를 고쳐야 합니다. limit만 올리면 죽는 시점이 늦춰질 뿐입니다. 평평하게 유지되다 limit 근처에서 죽으면 limit 상향이 맞습니다.
2. **requests와 limits 재설정**: 관측한 피크(p99)에 20~30% 여유를 더해 limit으로 잡고, `requests`는 평상시 사용량에 맞춥니다. 가능하면 `requests.memory`와 `limits.memory`를 같게 하면 QoS가 Guaranteed가 되어 노드 압박 때 먼저 쫓겨나지 않습니다.
   ```yaml
   resources:
     requests: { memory: "768Mi" }
     limits:   { memory: "1Gi" }
   ```
3. **런타임 설정을 limit에 맞추기**
   - JVM: `-XX:MaxRAMPercentage=70` 정도로 설정합니다.
   - Node: `--max-old-space-size`를 limit의 약 75%로 설정합니다.
   - Go: `GOMEMLIMIT`을 limit의 약 90%로 설정합니다.
   - Python: gunicorn/celery의 워커 수와 `max-requests`(재활용)를 확인합니다.
4. **워커 동시성 줄이기**: 워커의 prefetch, concurrency, 배치 크기를 낮추면 피크 메모리가 줄어듭니다.
5. **HPA·VPA**: 메모리 기준 HPA를 쓴다면 스케일아웃이 OOM보다 먼저 일어나도록 하세요. VPA를 `Off` 모드로 돌리면 권장값을 얻을 수 있습니다.

`kubectl describe pod` 출력, 현재 resources 설정, 사용 언어·런타임을 알려주시면 API와 워커 각각에 맞는 구체적인 값을 제안해 드리겠습니다.

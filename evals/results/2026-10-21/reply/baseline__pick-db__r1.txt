샤딩은 맨 마지막 수단입니다. 4천만 행은 Postgres 단일 노드가 충분히 감당하는 규모이고, 보통 인덱스와 쿼리 문제로 느린 경우가 대부분입니다. 순서대로 해보시길 권합니다.

**1. 실제로 뭐가 느린지 측정**
- `pg_stat_statements`를 켜고 총 시간·호출 수 기준 상위 쿼리를 확인합니다.
- 느린 쿼리에 `EXPLAIN (ANALYZE, BUFFERS)`를 실행합니다. Seq Scan, 큰 Sort, 많은 `Rows Removed by Filter`, 높은 shared read가 보이면 원인을 찾은 겁니다.
- `auto_explain`과 `log_min_duration_statement`로 운영 중 느린 쿼리를 잡습니다.

**2. 인덱스 점검 (가장 효과가 큰 경우가 많음)**
- 목록 화면: `WHERE` 조건과 `ORDER BY`를 함께 덮는 복합 인덱스를 만듭니다. 예를 들어 `(status, created_at DESC)`처럼 정렬 방향까지 맞추면 정렬 비용이 사라집니다.
- 대부분의 행이 조회 대상이 아니면(예: 활성 데이터만 조회) 부분 인덱스(`WHERE deleted_at IS NULL`)가 작고 빠릅니다.
- 필요한 컬럼만 읽는 쿼리는 `INCLUDE`로 covering index를 만들어 index-only scan을 노립니다.
- 검색 화면: `LIKE '%키워드%'`는 B-tree를 못 탑니다. `pg_trgm` + GIN 인덱스나 `tsvector` 전문 검색을 쓰세요. 한국어 형태소 분석이 필요하면 별도 검색 엔진(Elasticsearch/OpenSearch)이나 `pgroonga` 같은 확장을 고려하세요.
- 안 쓰는 인덱스와 중복 인덱스는 쓰기와 캐시 효율을 해치니 `pg_stat_user_indexes`로 찾아 정리합니다.

**3. 쿼리·애플리케이션 패턴**
- `OFFSET` 페이지네이션은 뒤로 갈수록 느려집니다. keyset(커서) 방식으로 바꾸세요: `WHERE (created_at, id) < (:last_created, :last_id) ORDER BY created_at DESC, id DESC LIMIT 20`.
- 목록 화면의 `COUNT(*)`는 전체 스캔을 유발합니다. 정확한 총 개수를 포기하거나(“다음 페이지 있음”만 표시), 근사치나 캐시를 쓰세요.
- `SELECT *`를 줄이고, N+1 쿼리가 없는지 확인합니다.
- 자주 쓰는 집계는 materialized view나 별도 요약 테이블로 만듭니다.

**4. 테이블·DB 관리**
- `VACUUM`/autovacuum 상태와 bloat를 확인합니다. dead tuple이 많으면 느려집니다. 필요하면 autovacuum 설정을 공격적으로 조정하세요.
- `ANALYZE`로 통계가 최신인지 확인합니다. 필요하면 `default_statistics_target`을 높입니다.
- 메모리 설정을 점검합니다: `shared_buffers`, `effective_cache_size`, `work_mem`. 작업 집합이 RAM에 안 들어가면 디스크 I/O가 병목입니다.
- 스토리지가 느린 디스크(IOPS 부족)가 아닌지도 확인합니다.

**5. 그래도 부족할 때, 샤딩 전에 쓸 수단**
- **읽기 복제본(read replica)**: 목록·검색 같은 읽기 트래픽을 분리합니다. 읽기가 문제라면 가장 직접적인 해법입니다. 복제 지연은 감안해야 합니다.
- **캐시**(Redis 등): 인기 목록이나 검색 결과를 캐시합니다.
- **파티셔닝**(declarative partitioning): 시간이나 테넌트 기준으로 나누면 파티션 프루닝으로 스캔 범위가 줄고 오래된 데이터 관리도 쉬워집니다. 단일 DB 안에서 하는 거라 샤딩보다 훨씬 간단합니다. 단, 쿼리가 파티션 키를 조건에 포함해야 효과가 있습니다.
- **더 큰 인스턴스**: 수직 확장이 샤딩보다 훨씬 쌉니다.

**샤딩은 언제?**
쓰기 처리량이 단일 노드 한계를 넘었거나, 데이터가 수 TB 이상으로 커져 위 방법을 다 써도 안 될 때 고려합니다. 읽기 위주의 4천만 행에서는 해당될 가능성이 낮고, 도입하면 조인, 트랜잭션, 운영 복잡도가 크게 늘어납니다.

원하시면 느린 쿼리 하나와 `EXPLAIN (ANALYZE, BUFFERS)` 결과, 테이블 스키마를 보내주세요. 구체적으로 어떤 인덱스나 쿼리 수정이 필요한지 짚어드리겠습니다.

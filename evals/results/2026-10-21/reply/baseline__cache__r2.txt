코드를 보지 않고 일반적인 원인으로 답합니다. 최대 10분이라는 수치는 캐시 TTL이 10분(600초)이고 가격 변경 시 캐시를 무효화하지 않는 경우와 정확히 맞습니다.

## 왜 그런가

보통 cache-aside 패턴을 씁니다.

1. 읽기: Redis를 먼저 조회하고, 없으면 DB에서 읽어 `SET key value EX 600`으로 저장합니다.
2. 쓰기: DB의 가격만 UPDATE하고 Redis 키는 건드리지 않습니다.

그래서 DB는 새 가격이어도 Redis에는 마지막으로 채워진 시점부터 최대 10분간 옛 값이 남습니다. 목록과 상세 둘 다 그런 이유는 두 가지 중 하나입니다.

- 둘 다 같은 상품 캐시를 읽습니다.
- 목록 캐시(예: `products:list:{category}:{page}`)에 가격이 복사되어 들어 있어서, 상세 캐시와 별개로 같은 문제가 생깁니다.

## 어떻게 고치나

**1. 가격 변경 시 캐시 무효화 (기본 해결책)**

DB 커밋 후에 해당 키를 `DEL`합니다. 순서는 DB 업데이트, 커밋, 캐시 삭제입니다. 갱신(SET)보다 삭제가 안전합니다. 동시 요청이 옛 값으로 캐시를 덮어쓰는 경합이 줄기 때문입니다.

```python
with db.transaction():
    db.execute("UPDATE product SET price=%s WHERE id=%s", (price, pid))
# 커밋 이후
redis.delete(f"product:{pid}")
```

**2. 목록 캐시 처리**

목록 키는 상품 ID로 추적하기 어렵습니다. 방법은 세 가지입니다.

- **구조 분리 (권장)**: 목록 캐시에는 상품 ID 순서만 두고, 가격 같은 상세 정보는 `product:{id}`에서 `MGET`으로 합칩니다. 그러면 1번만으로 목록도 해결됩니다.
- **버전 키**: `products:list:v{version}:...` 형태로 두고, 가격이 바뀌면 version을 `INCR`합니다. 옛 키는 TTL로 사라집니다.
- **짧은 TTL**: 목록만 TTL을 30~60초로 줄입니다. 가장 간단하지만 완전한 해결은 아닙니다.

**3. 보완 장치**

- **삭제 실패 대비**: 삭제가 실패하거나 경합이 생길 수 있으니 TTL은 안전망으로 남기고, 필요하면 지연 이중 삭제(수백 ms 뒤 재삭제)를 씁니다.
- **여러 서버에서 변경하는 경우**: 가격 변경 경로가 여러 곳(어드민, 배치, 외부 연동)이면 모든 경로에서 무효화해야 합니다. 서비스 레이어 한 곳으로 모으거나, outbox/CDC(Debezium 등)로 DB 변경을 감지해 캐시를 지우면 누락을 막을 수 있습니다.
- **다른 캐시 계층**: CDN, API 게이트웨이, 브라우저의 `Cache-Control`도 확인하세요. Redis를 고쳐도 10분이 그대로면 다른 계층이 원인입니다.

실제 코드(캐시 키 구조, 가격 변경 경로, TTL 설정)를 알려 주시면 정확히 어디를 고칠지 짚어 드리겠습니다.

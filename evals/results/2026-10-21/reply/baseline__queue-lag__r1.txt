**랙 200만이 나쁜지는 숫자만으로 알 수 없습니다.** 랙이 시간이 지나며 어떻게 움직이는지가 더 중요합니다.

## 먼저 볼 것

| 패턴 | 의미 |
|---|---|
| 피크 때 올라갔다가 **스스로 0 근처로 회복** | 일시적 버스트를 컨슈머가 따라잡는 정상 패턴일 가능성이 큼 |
| 올라간 뒤 **계속 유지되거나 우상향** | 컨슈머 처리량이 유입량보다 낮은 상태라 문제입니다. |
| 특정 **파티션만** 높음 | 파티션 키 쏠림(핫 파티션)이나 특정 컨슈머 인스턴스 문제 |
| 갑자기 평평하게 고정됨 | 컨슈머 중단, 리밸런싱 반복, 또는 poison message에 걸렸을 가능성 |

그래서 아래 두 가지를 같이 보세요.
- **랙을 시간(초)으로 환산:** `랙 ÷ 컨슈머 처리 속도(msg/s)`입니다. 처리 속도가 초당 1만 건이면 200만 랙은 약 200초(3분 남짓)입니다. 초당 500건이면 약 67분입니다.
- **유입 속도 대비 처리 속도:** 처리 속도가 유입 속도보다 높아야 랙이 줄어듭니다.

## 주문·결제에서 사용자가 겪는 일

랙은 "이벤트가 발행됐지만 아직 처리되지 않은 양"입니다. 처리 지연이 길어지면 다음과 같은 증상이 나타납니다.

- 결제는 끝났는데 **주문 상태가 "결제 대기"로 계속 남아 있음**
- 주문 완료 알림, 문자, 이메일이 **늦게 도착함**
- 재고 차감과 쿠폰·포인트 반영이 늦어져 **중복 사용이나 초과 판매** 가능성
- 사용자가 "안 된 줄 알고" **재결제 시도 또는 CS 문의**
- 결제 타임아웃 후 **자동 취소 로직과 늦게 도착한 결제 완료 이벤트가 충돌**

지연이 몇 초에서 몇 분 수준이면 대부분 체감하지 못합니다. 수십 분을 넘기거나 상태 불일치가 생기면 사용자 영향이 큽니다.

## 확인 순서

1. 랙 추이가 회복형인지 정체형인지 봅니다. 최근 며칠 치를 같이 비교하세요.
2. 파티션별 랙 편차를 확인합니다.
3. 컨슈머 처리 시간(DB, 외부 API 호출)과 리밸런싱 빈도, 에러·재시도 로그를 봅니다.
4. 컨슈머 수가 파티션 수보다 적은지 확인합니다. 컨슈머를 늘려도 파티션 수 이상으로는 병렬화되지 않습니다.
5. 메시지 보관 기간(retention) 대비 랙 크기를 확인합니다. 랙이 retention을 넘으면 데이터가 유실됩니다.

## 알림 기준 제안

절대 랙 수치보다 **"랙이 N분 이상 지속적으로 증가"** 또는 **"예상 소진 시간이 임계값 초과"** 로 알림을 거는 편이 오탐이 적습니다. Burrow나 Kafka Lag Exporter 같은 도구가 이런 판정을 지원합니다.

토픽의 파티션 수, 컨슈머 수, 평소 유입 TPS를 알려 주시면 이 200만이 위험한 수준인지 더 구체적으로 짚어 드리겠습니다.

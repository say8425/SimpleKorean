| 파일 | 내용 |
|---|---|
| `prompts.json` | 질문 16개. `id`, 질문 유형(`type`), 출처(`source`), 질문 문장(`prompt`) |
| `policies.json` | 정책마다 바꾼 답변 문단 두 개(`paragraph_1`, `paragraph_3`) |

## 만든 방법

규칙 블록은 커밋 `0b1b302`의 `prompts/system-prompt.md`를 썼다. 정책마다 답변 문단 두 개만 `policies.json`의 문장으로 바꿨다. 나머지 문장은 모든 정책에서 같다. 조건은 다섯 가지다:

- `baseline`: 규칙 블록 없음
- `prohibit`: 서술형만 쓰게 하고 헤더와 목록을 막음
- `permit`: 헤더와 목록을 써도 되고, 쓸지는 모델이 정함
- `mandate`: 주제가 둘 이상이고 세 문단 이상인 답은 헤더로 나누게 함(앞선 PR #10 문구)
- `permit_plus`: `permit`에 원인과 결과를 문장으로 잇게 하는 문장을 더함

답은 `claude-sonnet-5-5`가 effort low로 썼다. `evals/bench_common.py`의 격리 실행(`claude -p`, 사용자 설정과 MCP 서버 없음)을 썼다. 질문마다 두 번 답하게 했다.

판정은 같은 질문, 같은 회차의 두 답을 비교했다. 순서를 바꿔 두 번 물었고, 두 번 모두 같은 쪽을 고르면 그쪽이 이긴다. 아니면 무승부(`tie`)다. 기준은 세 가지다:

- `understand`: 분야를 잘 모르는 독자가 한 번 읽고 내용과 이유를 정확히 이해하기 쉬운 답
- `find`: 나중에 다시 볼 때 원인, 할 일, 명령을 빨리 찾을 수 있는 답
- `overall`: 질문한 사람이 받고 싶은 답

Opus에게는 한국어 판정 문장을 주고 JSON으로 답하게 했다. 판정 기록의 `order1`과 `order2`에 두 순서의 답과 이유(`reason`)가 있다. Jev에게는 같은 기준을 영어 Choice 질문으로 물었다. `p_x`는 앞 조건이 이길 확률을 두 순서에서 평균한 값이다.

## 분석에 쓴 정의

- 조각 항목: 목록 항목에서 인라인 코드를 뺀 뒤 "다", "요", "죠", "까"로 끝나지 않는 항목이다.
- 연결어: "때문", "그래서", "따라서", "하지만", "그러나", "그러면", "그러므로", "므로", "반면", "대신"이 나온 횟수다. 코드 블록은 세지 않는다.
- 답변 결함과 문장 수는 `evals/ko_lint.py`의 `reader_check`로 셌다.
- 길이 통제는 두 답의 글자 수 차이가 긴 쪽의 20% 미만인 쌍만 따로 센 것이다.

넣지 않은 것은 Jev 응답 캐시와 판정 모델의 원래 출력 전문이다. 판정 결과와 이유는 판정 기록에 모두 들어 있다.

## 1. 목표

SimpleKorean은 LLM이 기술 문서와 채팅 답변을 쉬운 한국어로 쓰게 하는 에이전트 스킬이다. AminBlg/SimpleEnglish의 한국어 파생 프로젝트이고, 원본처럼 Agent Skills 표준 스킬과 Claude Code·Codex 플러그인으로 배포한다.

- 독자: 한국어로 기술 문서를 쓰면서 AI 에이전트를 쓰는 개발자. 그 문서를 읽는 사람은 분야 밖의 똑똑한 독자다.
- 성공 기준:
  1. 스킬이 켜져 있으면 꺼져 있을 때보다 독자가 보는 결함(서식, 번역투, AI 슬롭, 비지정 표기)이 측정 가능한 만큼 준다.
  2. README에 실은 모든 수치를 커밋한 원본 파일에서 다시 계산할 수 있다.
  3. 스킬 문서가 스킬 자신의 규칙을 지킨다. CI가 이것을 검사한다.
- 설계 원칙: 영어 규칙을 번역하지 않는다. 원본 규칙마다 막으려던 오독을 찾고, 한국어 문법으로 같은 오독을 막는 규칙을 세운다. 한국어 규칙마다 대응하는 원본 규칙 번호를 적는다.

## 4. 문서 규칙 (기본 모드)

### 4.1 규칙 대응표

| # | 원본 규칙 | 한국어 규칙 |
|---|---|---|
| 1 | 절차/설명 구분, 문장당 20/25단어 | 글을 절차문과 설명문으로 나눈다. 절차문은 "-하세요"로 쓰고, 한 문장에 동작 하나, 15어절 이하다. 설명문은 "-습니다"로 쓰고, 한 문장에 명제 하나, 20어절 이하다. 문단마다 주제는 하나, 문장은 6개 이하다 |
| 2 | 코드·식별자·사실은 손대지 않음 | 코드, 식별자, 명령, 플래그, 경로, 인용한 오류 문구, 제품 이름, 사실은 바꾸지 않는다. 제품 이름과 식별자를 음차하거나 번역하지 않는다. 원문에 숫자나 원인이 없으면 일반 진술을 그대로 둔다 |
| 3 | 조건을 명령 앞에 | 조건은 "-면"으로 명령 앞에 둔다. "만약"을 붙이지 않는다. 명령 뒤에 "단, ~경우"를 덧붙이지 않는다 |
| 4 | 단순 시제, 능동태, 현재완료와 "-ing" 절 금지, 행위자 명시 | 단순 현재와 단순 과거로 쓴다. 진행이 아닌데 "-고 있습니다"를 쓰지 않는다. 이중 피동("-되어지다", "보여지다")을 쓰지 않는다. "~에 의해 ~되다"는 행위자를 주어로 바꾼다. "-함으로써"로 결과를 덧붙이지 않고 새 문장으로 쓴다. 행위자가 중요하면 밝힌다("sqlpipe가 행을 지웁니다") |
| 5 | can/will/must만 | 양태는 "-ㄹ 수 있습니다", 현재형, "-해야 합니다"만 쓴다. 4.3의 사다리로 고친다 |
| 6 | 축약 금지, 관사와 that 유지, 전보문체 금지 | 조사를 빼지 않는다. 본문 문장을 명사형("-함", "-음", "-임", "-필요")으로 끝내지 않는다. 구어 축약("겁니다", "근데")을 쓰지 않는다. 한 문서에는 문체 하나만 쓴다(4.2) |
| 7 | 세미콜론, em-dash 금지 | 같다. 두 문장으로 쓰거나 관계를 말로 밝힌다 |
| 8 | 한 단어 한 뜻, 명사 나열 3개 이하 | "확인하다"(확인·검증·점검·체크·검사 대신)와 "설정"(설정·구성 파일·컨피그 대신)으로 통일한다. 명사 나열은 3개까지이고, 더 길면 조사나 동사로 푼다("연결 풀의 타임아웃 값"). "진행하다", "수행하다", "실시하다"를 붙이지 않고 동사 하나로 쓴다("배포를 진행합니다" → "배포합니다") |
| 9 | 용어와 사실을 필요한 단계 앞에, 개념 용어 정의 | 개념 용어는 처음 쓸 때 열 어절 이하로 풀이한다. 번역한 기술 용어는 처음 한 번 원어를 괄호에 함께 쓴다("멱등성(idempotency)"). 제품 이름, 표준 이름(Postgres, S3, HTTP), 문서가 다루는 도구는 풀이하지 않는다. 명령이 기대는 호스트, 플래그, 앞 단계를 밝힌다 |
| 10 | 중요성 말고 사실 | 사실을 쓰고 중요성은 쓰지 않는다. 사실을 담지 않은 말(원활하게, 강력한, 손쉽게, 획기적인)을 지운다. 번역투(4.4)를 고친다. "단순히 X가 아니라 Y입니다", 장식용 세 항목 나열, "결론적으로"로 시작하는 문단을 쓰지 않는다 |
| 11 | 구조를 나타낼 때만 서식 | 굵은 글씨로 시작하는 문단, 강조용 굵은 글씨, 이모지, 두 문장도 덮지 않는 제목을 쓰지 않는다. 세로 목록은 셋 이상의 나란한 항목이나 단계에 쓰고, 앞 문장은 쌍점으로 끝낸다. 항목은 모두 명사구이거나 모두 문장이다. 절차 단계는 완전한 문장이다 |
| 12 | 경고는 명령이나 조건을 먼저 | 명령이나 조건을 먼저 쓰고 위험을 다음에 쓴다. "경고:"는 사람이 다칠 위험, "주의:"는 데이터나 장비가 손상될 위험에 쓴다 |
| 13 | 미국식 철자 | 맞춤법, 외래어 표기법, 국립국어원 용례, 단어 목록을 따른다(4.5) |

### 4.2 문체

- 새 문서는 서술에 "-습니다", 지시에 "-하세요"를 쓴다. Microsoft, Mozilla, React, MDN, Vue 한국어 문서가 이 조합을 쓴다(보고서 1).
- 기존 문서를 고칠 때는 그 문서의 문체를 따른다. 예를 들어 Kubernetes 한국어 문서는 해라체다.
- UI 문구는 제품의 문체를 따른다. 예를 들어 토스는 해요체다.
- 한 문서 안에서 "-습니다"와 해라체("-다"), 해요체 평서("-요")를 섞지 않는다. "-하세요"와 "-하십시오"도 섞지 않는다.

### 4.3 양태 사다리

| 쓴 표현 | 고칠 표현 |
|---|---|
| "-해야 할 것 같습니다", 필수인데 쓴 "-하는 것이 좋습니다" | "-해야 합니다" |
| 권고하는 "-하는 것이 좋습니다" | 지우거나 사실로 쓴다: "X가 Y보다 빠릅니다." |
| "-ㄹ 수도 있습니다", "-ㄹ 것 같습니다", "-로 보입니다" | "-ㄹ 수 있습니다", 또는 근거와 함께 사실로 쓴다 |
| "-ㄹ 것입니다" (영어 will의 직역) | 현재형: "다음 버전에서 제거됩니다." |
| "-하시기 바랍니다" | "-하세요" |
| "아마" | 지우거나 근거를 쓴다 |

### 4.4 번역투 목록 (초기)

"에 대해/에 대한", "을/를 통해", "에 의해/에 의한", "에 있어(서)", "을/를 가지고 있다", "로 인해/로 인한", "하는 것이 가능하다", "이/가 요구된다", "할 필요가 있다", "에 위치한", "만약/만일", 진행이 아닌 "고 있습니다", "(으)로부터".

근거는 이근희(2008)의 번역투 빈도표, Microsoft 한국어 스타일 가이드, Kubernetes 한글화 가이드다(보고서 1). 대체 표현은 `references/word-swaps.md`에 둔다.

### 4.5 표기 규칙

| ③ 관용이 굳음 (4개) | 레포지토리←리포지토리·레포지터리·레포, 바디(잡을 형태 없음), 칼럼←컬럼, 대상←타겟 | 경고 | 오류. 규범형 리포지터리, 보디, 타깃에는 "지정형이 아님" 경고 |
| ④ 공식 표기 없음 (2개) | 리디렉션(동사 "리디렉션하다")←리다이렉트·리디렉트, 리팩터링←리팩토링 | 문서 안 혼용만 경고 | 경고 |
| ⑤ 외래어와 우리말 중 선택 (5개) | 오류←에러, 매개변수←파라미터, 사용자←유저, 기본값←디폴트, 배포←디플로이 | 문서 안 혼용만 경고 | 경고 |
| ⑥ 띄어쓰기 (4개) | 기본값←기본 값, 매개변수←매개 변수, 반환값←반환 값, 오픈소스←오픈 소스 | "기본 값"만 경고, 나머지는 혼용만 경고 | "기본 값"은 오류, 나머지는 경고 |
| 전체 | 문서 안 일관성 (한 개념에 한 형태) | 경고. 기준은 문서에 먼저 나온 형태 | 오류. 기준은 지정형 |

③의 근거와 처리는 다음과 같다.
- 규범형 리포지터리와 보디는 벤더 문서와 현지화에서 거의 쓰이지 않는다. 벤더 문서 표본에서 리포지터리는 1,104회 가운데 0회였고, 보디는 현지화와 벤더 문서 205회 가운데 0회였다(보고서 2).
- 레포지토리와 바디는 사용자 결정(2026-10-08)이다. 목록 항목에 "규범형은 실사용이 거의 없어 관용형을 지정"이라는 근거를 남긴다.
- 엄격 모드 메시지는 "규범 위반"이라고 쓰지 않고 "SimpleKorean 지정형은 X"라고 쓴다.
- 칼럼은 규범형이고, 대상은 우리말 대응어다. 저장소, 본문, 열, 타깃은 쓸 수 있는 말이라 기본 모드에서 잡지 않는다.

검사하지 않는 곳은 다음과 같다.
- 코드 블록, 인라인 코드, URL, 파일 경로
- 따옴표("…", '…', 「…」)로 인용한 부분
- 제품·앱 이름(예: 디렉토리 유틸리티)과 API 객체 이름(예: 디플로이먼트)
- 앞에 한글이 붙은 합성어(예: 모노레포, 앱쉘, 하이퍼파라미터)
- 명시한 예외(캐시백, 레포트, 텔레포트, 쉘프, 컨버전, 이해시키다)
- `<!-- simple-korean: off -->`와 `<!-- simple-korean: on -->` 사이

프로젝트 설정(`.simple-korean.json`, 8.5)으로 ②~⑥의 지정형을 바꿀 수 있다. 예를 들어 토스처럼 릴리즈·컬럼, 카카오처럼 파라미터, Kubernetes처럼 리포지터리를 고를 수 있다. ①을 바꾸려면 이유(`reason`)를 적어야 한다. 앱과 애플리케이션은 둘 다 규범형이라 일관성 쌍으로 묶지 않는다.

근거의 무게는 다음 순서다: 국립국어원 판정, 근거를 기록한 사람의 용어집 결정, 2023년 이전 사람 글과 편집된 코퍼스, 2026년 편집 안 된 글. 2026년 글에는 LLM 문체가 섞였을 수 있으므로(velog의 em dash 비율이 0~2%에서 약 19%로 증가) 2026년 빈도만으로 단어의 무리를 옮기지 않는다.

### 4.6 문장 길이 세는 법

- 어절은 공백으로 나눈 단위다.
- 인라인 코드, URL, 숫자와 단위("5 GB"), 괄호 안의 글은 앞 어절에 붙여 한 어절로 센다.
- 코드 블록과 제목은 세지 않는다.
- 목록 항목과 표의 칸은 각각 한 단위다. 쌍점으로 끝나는 앞 문장도 한 문장이다.
- 문장 유형은 끝으로 가린다. "-세요", "-십시오", "-하라", "-하자"로 끝나면 절차문(15어절)이고, 나머지는 설명문(20어절)이다. 린터의 `--type`은 끝으로 가릴 수 없는 문장에 쓸 기본값이다.
- 15와 20은 한국어 실증 근거가 없는 설계 값이다(보고서 1). README에 그렇게 밝힌다.

### 4.7 자가 점검

SKILL.md의 자가 점검 절은 두 가지다.
1. 답변: `—`, `**`, `#`, `-`로 시작하는 줄을 찾아 없앤다.
2. 문서: 가장 긴 세 문장의 어절을 세고, 상한을 넘으면 나눈다. 다음을 찾아 고친다.
   - 번역투(4.4)와 "-고 있습니다"
   - 양태 사다리(4.3)의 금지 표현
   - "진행합니다", "수행합니다"
   - "확인" 외의 검증 동사, "설정" 외의 이름
   - 명사형으로 끝난 문장, 두 문장도 덮지 않는 제목
   - 단어 목록의 비지정 표기

   단계마다 필요한 호스트, 플래그, 앞 단계를 밝혔는지 확인한다.

## 5. 답변 규칙 (모든 모드)

1. 서술형으로 답한다. 헤더, 불릿, 굵은 글씨, 표를 쓰지 않는다. 독자가 복사해야 하는 코드는 코드 블록에 둔다.
2. 첫 문장에 답이나 결과를 쓴다. 질문을 되풀이하지 않고, "네, ~에 대해 설명드리겠습니다"로 시작하지 않는다.
3. em-dash를 쓰지 않는다. "때문에", "하지만", "예를 들어"로 관계를 밝히거나 두 문장으로 나눈다.
4. 개념 용어는 처음 쓸 때 짧게 풀이한다("멱등(같은 요청을 여러 번 보내도 결과가 같음)"). 제품 이름은 풀이하지 않는다.
5. 한 답변 안에서는 문체를 하나만 쓴다. 기본은 "-습니다"이고, 사용자가 다른 문체를 요청하면 그 문체를 쓴다. 인사말("좋은 질문입니다", "물론입니다")과 맺음말("도움이 되셨기를 바랍니다", "궁금한 점이 있으면 언제든지")을 쓰지 않는다. 원본의 "축약형 금지"를 바꾼 규칙이다.
6. 인용한 오류 문구, 보안 경고, 되돌릴 수 없는 작업 전의 확인 문구는 줄이지 않는다.

슬롭 어휘와 번역투 목록은 답변에도 적용한다.

## 6. 모드

- 기본 모드: 4장과 5장이다.
- 엄격 모드: 사용자가 "엄격 모드", "통제 언어", "KS A 0001", "STE", "ASD-STE100"을 말하면 켠다. `references/strict-mode.md`를 먼저 읽고 문서에만 적용한다. 답변은 기본 모드 그대로다. 켤 때 한 번만 이렇게 알린다: "한국어 통제 언어 국가 표준은 없으며, 이 기준은 KS A 0001과 공개 연구를 바탕으로 한 비공식 기준입니다."
- 점검 모드: 글을 쓰는 대신 점검을 요청받으면 `references/rule-catalog.md`를 먼저 연다. 위반마다 K 번호, 해당 문구, 고친 문장을 보고한다. 규칙 번호를 기억에 기대 인용하지 않는다. 엄격 모드로 점검했으면 끝에 위의 비공식 기준 고지를 한 문장 붙인다.
- 한계: 이 규칙은 설득하는 문장을 지운다. 마케팅이나 브랜드 글을 요청받으면 이 점을 알리고, 그 글이 링크할 문서에 규칙을 쓰자고 제안한다.

### 6.1 엄격 모드 규칙 (`references/strict-mode.md`)

KS A 0001:2023 부속서 I와 H의 요지를 다시 써서 출처를 단다. 표와 원문은 옮기지 않는다.
- 문장 끝은 다섯 가지만 쓴다.
  - 의무: "-해야 합니다"
  - 금지: "-하면 안 됩니다"
  - 허용: "-해도 됩니다", 불필요: "-하지 않아도 됩니다"
  - 능력과 가능성: "-ㄹ 수 있습니다". 허용의 뜻으로는 쓰지 않는다.
  - 사실과 예정: 현재형과 과거형
- 권고형("-하는 것이 좋습니다", "-하여야 할 것입니다")과 "-ㄹ 것입니다"를 쓰지 않는다. "반드시"는 법이나 규정 같은 외부 제약에만 쓴다.
- 접속어: "(이)나"를 쓰지 않는다. 두 항목은 "와/과", 셋 이상은 "및", 선택은 "또는"으로 잇는다. "이상·이하"는 기준값을 포함하고 "초과·미만"은 포함하지 않는다.
- 조건은 "-면"으로만 쓴다. "-ㄹ 경우"를 쓰지 않고, "-ㄹ 때"는 시점을 말할 때만 쓴다(임병화·남유선 2009).
- 번역한 기술 용어의 원어 병기는 필수다.
- 단어 목록은 4.5 표의 엄격 모드 강도로 검사한다.
- 규칙마다 근거(KS A 0001 조항, 학술 연구, 보고서의 절)를 적는다.

## 8. 린터 `evals/ko_lint.py`

### 8.1 인터페이스

- 원본 `ste_lint.py`와 같은 함수와 옵션을 둔다: `lint(text, text_type)`, `lint_detail(text, text_type)`, `reader_check(text)`, `--self-test`, `--type procedural|descriptive|reply`, `--gate`.
- 더하는 것은 다음과 같다.
  - `--strict`: 엄격 모드 강도로 검사한다.
  - `--config PATH`: 프로젝트 설정 파일이다. 없으면 대상 파일에서 위로 올라가며 `.simple-korean.json`을 찾는다.
  - `--gate`는 오류가 있으면 실패하고, `--gate=warning`은 경고까지 실패로 본다. 원본은 위반이 하나라도 있으면 실패했다.
- 표준 라이브러리만 쓰고, Python 3.9 이상에서 돈다(macOS 기본 python3).
- 결과에는 `errors_total`, `warnings_total`, `violations_total`, `violations_per_100_eojeol`, 범주별 수를 담는다. `lint_detail`의 항목마다 범주, 강도, 줄 번호, 문구가 있다.

### 8.3 한국어 매칭

- 입력을 NFC로 정규화한다.
- 단어 목록과 어휘 패턴은 어절 앞부분을 맞추고 뒤의 조사를 허용한다. 앞 글자가 한글이면 합성어로 보고 건너뛴다.
- 잡을 형태가 지정형이나 다른 형태의 앞부분이면(예: "레포"와 "레포지토리", "레포지터리") 긴 형태부터 맞추고, 이미 맞춘 자리는 다시 맞추지 않는다.
- "-ㄹ 것입니다"는 " 것입니다"나 " 것이다" 앞 음절의 받침이 ㄹ인지로 가린다(한글 음절 분해).
- 문체는 문장 끝 어미로 나눈다: 합쇼체 평서·의문("-니다", "-니까"), 합쇼체 명령("-십시오"), 해요체 명령("-세요"), 해요체 평서("-요"), 해라체("-다", "-라"). 허용 조합은 "합쇼체 평서 + 해요체 명령"과 "합쇼체 평서 + 합쇼체 명령"이다. 해라체만 쓴 문서와 해요체만 쓴 문서도 허용한다.
- 명사형 종결은 본문 문장에만 적용한다. 목록 항목, 표 칸, 제목은 건너뛴다.
- 4.5의 "검사하지 않는 곳"을 모든 어휘 검사에 적용한다. 따옴표 안을 건너뛰므로 규칙 설명에서 금지 표현을 언급해도 걸리지 않는다.
- 한계: 정규식 검사이고 형태소 분석을 하지 않는다. 거짓 일치와 놓침이 있다. 숫자는 같은 린터 버전끼리 비교하는 값이고 준수 판정이 아니다. README와 모듈 설명에 이 한계를 적는다.

### 8.4 데이터

`data/terms.json`의 형식은 다음과 같다.


`evals/slop.tsv`의 형식은 원본처럼 "용어, 등장 목록 수, 대체어" 세 열이다.
- `tools/slop-lexicon/`의 스크립트가 공개된 한국어 AI 문체 목록들에서 용어를 뽑는다. 후보는 im-not-ai, humanizer-ko, korean-writing, tech-doc-kr이고, 라이선스를 확인한 목록만 쓴다.
- 여러 목록에 함께 나온 용어를 고른다. 문턱 값은 목록 수를 보고 구현 때 정하고 README에 적는다.
- 출처 목록은 `tools/slop-lexicon/sources.json`과 NOTICE에 둔다.
- 린터는 파일이 없으면 코드 안의 핵심 목록으로 돈다.

`data/basic-vocabulary/`에는 국어 기초 어휘 등급 목록(2023)에서 표제어, 품사, 등급만 뽑은 TSV와 출처 표시를 둔다. "의미" 열은 싣지 않는다. 측정 스크립트만 이 데이터를 쓴다.

### 8.5 프로젝트 설정 `.simple-korean.json`

```json
{
  "terms": {
    "repository": "리포지토리",
    "release": {"write": "릴리즈"},
    "method": {"write": "메소드", "reason": "TTA 정보통신용어사전을 따름"}
  },
  "skip": ["디렉토리 유틸리티"],
  "spacing": "attached"
}
```

- `terms`: 개념 id마다 지정형을 바꾼다. ① 무리를 바꾸면서 `reason`이 없으면 린터가 경고한다.
- `skip`: 검사하지 않을 문자열이다.
- `spacing`: "attached"(기본) 또는 "spaced"다. Microsoft나 GitHub 문서를 옮기는 프로젝트는 띄어 쓰는 쪽을 고를 수 있다.

### 8.6 자체 시험

원본 구성에 맞춰 한국어 고정 예문을 둔다.
- 슬롭 예문: 모든 범주가 1회 이상 걸린다.
- 깨끗한 예문: 위반이 0이다.
- 표, 목록, 굵은 이름표 목록 예문: 문장 길이 거짓 일치가 없다.
- 대시 예문: 논리 연결 대시만 걸리고, 범위와 플래그는 걸리지 않는다.
- 답변 예문: `reader_check`의 수가 정해진 값과 같다.
- 문체 혼용 예문, 표기 예문(합성어와 예외는 걸리지 않음), 엄격 모드 예문, 꺼짐 표시 예문

`lint_detail`의 항목 수와 `lint`의 총계가 같은지도 확인한다.

## 11. 측정

### 11.1 순서

1. 보정: 원본의 규칙을 지킨 영어 예문(README와 SKILL.md, `examples/before-after.md`의 '후' 문장)을 한국어로 옮긴 문장이 모두 통과하는지 확인한다. 기준선 출력에서 린터의 거짓 일치가 얼마나 나오는지도 확인한다. 그 결과로 어절 상한과 패턴을 확정하고, 바뀐 값을 CHANGELOG에 남긴다.
2. 기준선 오염 확인: `claude -p --setting-sources ""`의 init 이벤트에 사용자 플러그인, 훅, MCP 서버가 없는지 확인한다. 탐침 질문으로 사용자 CLAUDE.md와 규칙 파일이 섞이지 않는지도 확인한다.
3. 본 측정(11.2)을 돌린다.
4. 원본 출력을 커밋하고 RESULTS.md를 쓴 뒤, `check_numbers.py`로 README 수치를 검증한다.

### 11.2 설계

| 항목 | 값 |
|---|---|
| 모델 | `claude-sonnet-5-5`, effort low. 판정 모델은 `claude-opus-5-5`. 선택 교차 확인은 `claude-haiku-4-5-20251001` 1회 |
| 격리 | `--setting-sources ""`, 원본과 같은 `--disallowedTools`, 빈 임시 작업 디렉터리 |
| 문서 | 과제 8개 × (기준선, 기본, 엄격) × 2회 = 48회. 과제는 원본 sqlpipe 과제를 한국어로 옮기고, 분량은 글자 수로 정한다 |
| 답변 | 질문 8개 × (기준선, 기본) × 2회 = 32회. 질문마다 전문용어가 하나씩 있다: 멱등성, 샤딩, TLS, 컨슈머 랙, OOMKilled, 토큰 버킷, 백필, 캐시 무효화 |
| 판정 | 답변 16쌍(기준선 대 기본)에서 "분야 밖 독자가 한 번에 이해하는 쪽"을 고른다. 앞 선택지 편향을 없애려고 순서를 바꿔 두 번 묻는다 = 32회. 두 번 모두 같은 쪽이면 그쪽의 승, 갈리거나 둘 다 비기면 무승부다 |
| 합계 | 약 112회 (선택 교차 확인 제외) |
| 스킬 주입 | 답변은 `--append-system-prompt`로 `prompts/system-prompt.md`의 규칙 블록을 넣는다. 문서는 원본처럼 SKILL.md 본문을 과제 앞에 붙이고, 엄격 조건은 `strict-mode.md`까지 붙인다 |

### 11.3 지표

- 헤드라인(독자가 보는 것): 답변의 em-dash, 굵은 글씨, 헤더, 불릿 수(원본과 같은 정의), 인사말과 맺음말 수, 판정 승·무·패

- 쉬운 단어 비율: 형태소 분석으로 뽑은 내용어(명사, 동사, 형용사, 부사) 가운데 국어 기초 어휘 1등급 표제어의 비율이다. `evals/metrics.py`에서만 선택 의존성으로 형태소 분석기를 쓴다. 의존성이 없으면 이 지표만 건너뛴다.
